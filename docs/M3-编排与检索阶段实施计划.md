## 执行说明

**Goal**：把 M1 留下的两处临时实现（规则路由、纯关键词检索）替换为 **LangGraph 状态图 + 自研混合检索 + LLM 带引用问答**，并补上新音频的 **LLM 纪要生成**，让 M2 的占位纪要实现退场。

**Architecture**：图只做编排（`StateGraph` + 条件边 + 重试循环），节点一律写成不依赖框架的纯函数；检索层在 M1 的「过滤 → BM25 → 阈值 → 组装 → 拒答」流水线上插入向量召回与 RRF 融合；LLM 只经 `LLMClient` 协议访问（真实 / 缓存 / 假实现三态），结构化输出按四级降级处理。

**Spec**：本文档即 M3 的 spec 与实施计划，承接《技术方案》17 节 M3 行。M4 的 checkpointer + interrupt、M5 的 Langfuse 与完整评测报告**不在本文范围**（见第 15 节划界）。

## 1. 目标与验收口径

《技术方案》17 节对 M3 的定义是：

> **M3 编排与检索**：LangGraph 状态图（路由 / 澄清 / 拒答 / 重试）；自研混合检索；带引用的问答。

结合 M1/M2 的实际状态，M3 的验收口径具体化为 7 条：

1. `POST /api/chat` 由 LangGraph 状态图驱动，**条件边与重试可断言**（不是把 M1 的顺序函数换个壳）；
2. 意图路由 = 模型结构化输出 + 规则兜底，且**关掉模型仍能跑通（默认就是关）**；
3. 检索层补齐向量召回与 RRF 融合，参数可逐项扫描，拒答仍在调用模型之前完成；
4. 回答由 LLM 基于证据片段合成，每条结论绑定片段 ID，前端渲染契约不变；
5. 上传真实音频后由 LLM 生成结构化纪要（map-reduce + schema 校验 + 重试 + 单条降级），M2 的占位纪要退场；
6. 多轮上下文可用：最近若干轮原文 + 更早轮次摘要，查询范围能跨轮继承；
7. 成本可量化：每轮回答记录模型、token、费用，重复提问命中缓存计 0。

**建议验收阈值**

| 验收项 | 口径 | 目标值 |
| --- | --- | --- |
| 自动化测试 | `pytest`（无网络 / 无模型 / 无 Key） | 全绿；用例数 154 → **≥ 200** |
| 事件契约 | SSE 事件名与载荷 | 与 M1 逐字段一致（回归用例） |
| 意图路由 | 固定 query 集（≥ 30 条，覆盖三条路径 + 澄清 + 拒答） | 准确率 **≥ 90%**；`MA_ROUTE_MODE=rules` 时不依赖模型 |
| 检索效果 | 标注 query 集 Recall@8、MRR | Recall@8 **≥ 0.80**；MRR 高于 M1 纯 BM25 基线（附前后对比表） |
| 拒答 | 域外 query（≥ 8 条，含现有 4 条） | 拒答正确率 **100%**，且拒答路径 LLM 调用次数 **0** |
| 证据可靠性 | 回答中引用 ID 可解析率 | **100%**；构造无支撑结论时被拦截（用例断言） |
| 纪要质量 | schema 合法率（含注入非法 JSON 的重试与降级） | **100%**；单条解析失败不导致整场会议失败 |
| 成本 | 单场 86.5s 会议 + 单次问答的 token / 费用 | 实测值写进验收报告；重复提问缓存命中 0 token |

阈值只是建议起点：真正的数字以 T8 的评测脚本在标注集上的实测为准，改参数必须附前后对比（《技术方案》9.3）。

## 4. 架构与文件结构

### 4.1 图结构（M3 版）

```text
START → route（模型 + 规则兜底）
  ├─ process_audio → create_task → END              # 长任务仍走后台线程 + tasks 表
  ├─ query_content → resolve_scope
  │                    ├─(范围不唯一且未指定)→ clarify → END
  │                    └─(已确定)→ retrieve（混合检索）→ grade
  │                                   ├─(不达标)→ refuse → END
  │                                   └─(达标)→ synthesize（LLM 结构化输出）
  │                                              → verify_evidence
  │                                                 ├─(引用全丢)→ 降级模板 / refuse
  │                                                 └─(通过)→ finalize → END
  ├─ query_speaker → aggregate_by_speaker → synthesize → verify_evidence → finalize → END
  └─ unknown → clarify → END
```

三条硬性规则：

- `refuse` 与 `clarify` 是**终止节点**，且**一次 LLM 都不调**（拒答先于生成，M1 已经是这个口径）；
- `grade` 是**唯一的阈值判定点**，判定不通过就不进 `synthesize`，因此"会不会编造"不取决于模型；
- `process_audio` 分支只建任务就结束，音频进度继续走 `GET /api/tasks/{id}/events`（M2 的后台执行模型不变）。

### 4.2 图只做编排，节点是纯函数

节点统一签名：

```python
def node_name(state: AgentState, ctx: NodeContext) -> dict: ...
```

- 节点不 import langgraph，只吃 `AgentState`（dict）与 `NodeContext`（`conn` / `settings` / `llm` / `encoder`）；
- `agent/graph.py` 是**全项目唯一 import langgraph 的地方**——和 `perception/transcribe.py` 是唯一 import faster-whisper 的地方同一条纪律；
- 因此节点测试**不需要装 LangGraph**：`tests/test_nodes_*.py` 直接调函数断言，只有 `tests/test_graph.py` 需要框架。

这套分层就是《技术方案》4.1 那句"框架出问题时的爆炸半径可控"的落地方式，也是面试里"可测试性"最直接的证据。

## 5. 关键设计

### 5.1 意图路由：模型优先、规则兜底、规则可强制

```python
class RouteDecision(BaseModel):
    intent: Intent                                   # process_audio | query_content | query_speaker | unknown
    answer_mode: AnswerMode                          # 决定装配形态（M1 已有枚举）
    meeting_ids: list[str] = []                      # 只允许出现库里真实存在的会议 ID
    speaker_id: str | None = None
    reason: str = ""
```

- `MA_ROUTE_MODE = auto | llm | rules`，默认 `auto`：
  - `auto`：先让模型做结构化输出；schema 校验失败、`intent=unknown`、或返回了不存在的 `meeting_id` → 回落到 M1 的 `routing.route()`；
  - `rules`：完全走规则表（断网演示的手动开关，也是评测基线）；
  - `llm`：只走模型，用于对比实验。
- 规则兜底保证 `intent` 永远落在枚举内，从不产生未知态；
- **模型给出的 `meeting_ids` 必须经过一次存在性过滤**——这是"模型不能凭空指定会议范围"的护栏，也避免了检索层拿到脏 ID。
- 测试：M1 的 `tests/test_routing.py` 全部保留（回归基线），新增"模型返回非法 intent → 回落规则""模型返回不存在的会议 ID → 被过滤"。

### 5.2 混合检索流水线（《技术方案》9.1 的 M3 落地）

```text
query
 ① 过滤      会议 / 发言人 / 时间区间（timefilter 解析「上周」「这周三」）
 ② 关键词    FTS5 BM25 召回 top-K1                （M1 已有）
 ③ 向量      查询向量 × 候选集向量 余弦 召回 top-K2 （新增，numpy）
 ④ 融合      RRF：score = Σ 1/(k + rank)，k = 60   （新增）
 ⑤ 阈值      向量余弦 top1 < τ 或 查询词覆盖率 < 0.34 → 丢弃
 ⑥ 重排      M3 默认 passthrough（协议留出，M5 再上 cross-encoder）
 ⑦ 组装      命中片段 + 相邻片段，按 token 预算裁剪并排序 （M1 已有，字符数 → token 估算）
 ⑧ 拒答      任一道闸不通过 → 不调用 LLM，直接 refuse
```

**两处与文档口径不同的实现决定，要能讲清理由：**

1. **RRF 分不用作绝对阈值。** RRF 只用排名，`1/(60+1) ≈ 0.0164` 这类分值没有跨查询可比性；用它卡阈值实际等于按"被几个召回列表命中"判相关性，换一批查询就失效。因此第 ⑤ 步用两个可解释量做绝对判定——**向量余弦 top1** 与**查询词覆盖率**——RRF 只负责融合排序。
2. **向量召回在候选集内做。** 先按过滤条件取出候选片段及其向量（一条 SQL，BLOB 解包成 numpy 矩阵），再做一次矩阵乘。这既是《技术方案》9.2 的"先过滤再检索"，也让"这场会"变成确定性条件而不是语义碰运气。

**参数表**（全部走 `config.py` + 环境变量，由 T8 的脚本扫描）

| 参数 | 默认值 | 环境变量 |
| --- | ---: | --- |
| 关键词召回条数 K1 | 50 | `MA_RECALL_K1` |
| 向量召回条数 K2 | 50 | `MA_RECALL_K2` |
| RRF 常数 k | 60 | `MA_RRF_K` |
| 上下文片段数 top-k | 8 | `MA_RETRIEVAL_TOP_K` |
| 向量余弦阈值 τ | 0.35 | `MA_MIN_COSINE` |
| 查询词覆盖率阈值 | 0.34 | `MA_MIN_COVERAGE` |
| 相邻片段窗口 | ±1 | `MA_NEIGHBOR_WINDOW` |
| 上下文预算 | 2400 token（估算） | `MA_TOKEN_BUDGET` |

| --- | --- | --- |
| `LocalBGEEmbedder` | 本地语义召回的默认实现 | `sentence-transformers` + `model/bge-small-zh-v1.5`（约 95 MB，走 `hf-mirror.com`） |
| `ApiEmbedder` | 云端 embedding（OpenAI 兼容 `/embeddings` 端点）：本地算力不够或想换更好的向量时启用 | `openai` SDK + `.env` 里的 Key |
| `HashingEmbedder` | 无权重机器的确定性兜底：字符 bigram 哈希到 256 维 + L2 归一化 | 纯标准库 |
| `FakeEncoder` | 测试用：返回预设向量，逐条断言召回与排序 | 无 |

选择规则与感知层 `factory.py` 同一套写法：`MA_TEXT_ENCODER = auto | bge | api | hash`，默认 `auto`，解析顺序是
**bge（本地权重就绪）→ api（配了 Key 且显式允许）→ hash（确定性兜底）**，并按顺序记录"为什么落到这一档"写进 trace
（用户看得见自己看到的是哪种检索质量）。`api` 不会被 `auto` 自动选中——它要走网络与计费，必须显式配置，
否则一次不经意的环境变量缺失就会把"本地可复现"变成"依赖外部服务"。

`segment_embeddings` 记录 `encoder` 与 `dim`，换编码器后旧向量不参与召回——沿用 M2 `speakers.encoder` 的做法：换模型后知道哪些向量失效。

两个实现共用同一条批处理接口，因此 `retrieval/pipeline.py` 不感知用的是本地还是云端；评测脚本可以一次跑出
"hash / bge / api" 三档召回对比。

### 5.4 结构化输出：四级降级（《技术方案》10.2 的落地）

落点 `app/llm/structured.py`：

```python
def complete_structured(
    client: LLMClient,
    messages: list[ChatMessage],
    model_cls: type[BaseModel],
    *,
    model: str,
    max_retries: int = 2,
) -> tuple[BaseModel | None, int, list[str]]   # (结果, 尝试次数, 每次的错误)
```

1. 供应商支持 `response_format={"type": "json_schema"}` → 直接约束 schema；
2. 只支持 JSON 模式 → `{"type": "json_object"}` + 提示词内嵌 schema；
3. Pydantic 校验失败 → 把 `ValidationError` 原文回填，重试最多 2 次；
4. 仍失败 → **条目级降级**：坏的那条标 `needs_review`，其余照常入库，整场会议不失败。

第 4 条是安全绳：一次会议里一条待办解析失败，不该让整场处理白跑。

### 5.5 成本控制与缓存

- `CachedLLMClient`（装饰器）：`prompt_hash = sha256(model + temperature + messages + schema)`，命中 `llm_cache` 直接返回，`cost=0`、`cached=True`；
- 成本累加：每次调用把 input/output token 与 cost 写回 `llm_cache`，并累加到本轮 `Answer.usage` 与 `chat_traces`；
- **断网演示兜底**：`MA_LLM_MODE = live | cache_first | off`，`warm_cache.py` 把常见问题预热进库，现场 `cache_first` 只读缓存，miss 时明确提示"需要联网"，而不是静默失败；
- 三档模型分开配置：`MA_LLM_MODEL_ROUTE`（便宜模型做路由）、`MA_LLM_MODEL_ANSWER`（合成）、`MA_LLM_MODEL_MINUTES`（纪要）——路由是低难度决策，没必要用最贵的模型（《技术方案》10.3）。

### 5.6 LLM 供应商切换与 `.env`

**决策 ① 的落地方式**：`MA_LLM_PROVIDER = openai` 是**协议名**，不是厂商名。
客户端永远走 OpenAI 兼容协议，换厂商只改 `.env` 里的 `base_url` + 模型名，代码一行不动
（《技术方案》4.2 的"供应商切换只改一处配置"）：

```ini

MA_LLM_BASE_URL=https://api.deepseek.com
MA_LLM_API_KEY=            # 用户填入
MA_LLM_MODEL_ROUTE=deepseek-flash
MA_LLM_MODEL_ANSWER=deepseek-flash
MA_LLM_MODEL_MINUTES=deepseek-flash
MA_LLM_MODE=live
```

- `app/config.py` 在读取环境变量**之前**用 `python-dotenv` 载入项目根目录的 `.env`；
  已存在的真实环境变量优先（部署环境覆盖本地文件）；
- `.env` 进 `.gitignore`，仓库只提交 `.env.example`；
- `MA_LLM_MODE` 默认值调整为 `auto`：**有 Key 则等价 `live`，没有 Key 则等价 `off`**，
  因此"新克隆的机器不配 Key 也不会误发请求"，C3 与"无 Key 可跑全部测试"同时成立；
- `provider` 取值校验只允许 `openai`（将来要接非 OpenAI 协议的厂商时，在这里加分支并补一组契约测试）。

### 5.7 多轮上下文

- `load_history(conn, conversation_id, recent_rounds=3)`：最近 3 轮保留原文；更早的合并成 `conversations.summary`（迁移 v3 加列），只在消息数超过阈值（默认 8 条）时用 LLM 重算一次；
- **scope 继承**：从上一轮 assistant 消息的 `answer.scope_meeting_ids` 继承，所以"那这场会还有什么风险"不依赖前端传 `meeting_id`；
- 预算：history + 证据 + 提示词共用同一个 token 预算（估算口径与 5.2 第 ⑦ 步一致）。

### 5.8 证据校验与"假流式"

- `synthesize` 产出的是**结构化 Draft**：每条 item 带 `evidence: list[segment_key]`，而不是自由文本里插引用标记——引用关系在结构上无法伪造；
- `verify_evidence` 在 M1 的两条规则（丢弃不存在的片段、引用全丢置 `warn`）之上增加可选一条：调用 LLM 判断"这个片段是否真的支撑这条结论"（`MA_VERIFY_MODE = rule | llm`，默认 `rule`，评测时做消融对比）；
- **不做 token 级流式**：先流式输出再校验会直接破坏 C4（引用错了收不回来）。M3 保持"先校验、后按块推送"的 `delta`：一次结构化生成，校验通过后按 item 分块 yield。这是有意的取舍，写进文档避免被追问时说不清。

### 16.3 与计划的显式偏差

1. **拒答的两个信号是"或"关系。** 计划第 5.2 节写的是"任一道闸不通过就拒答"，
   实现时发现那会让"用户换个说法提问"这类本可被语义救回的场景被覆盖率一票否掉。
   最终实现是：查询词覆盖率与向量余弦 top1 **任一达标即作答，两个都不达标才拒答**。
   《技术方案》9 节已同步这条口径。
2. **澄清 / 拒答 / 建任务也走 `verify_evidence → finalize`。** 计划里它们直接 `END`，
   实现改成统一经过校验与落库，让"每条结论都过证据校验"由图结构保证，
   而不是每个分支各自记得做。
3. **`min_cosine` 默认值由 0.35 改为 0.50。** 初始值在标注集上偏松（域外拒答正确率只有 0.25），
   扫参后取 0.50（拒答 1.000，域内召回与 MRR 不变）。
4. **向量存储键带维度后缀**（`encoder#dim`）。计划只写了 `encoder` + `dim` 两个字段，
   实现时发现同名不同维度会撞主键并互相覆盖，因此把维度并入身份键。
5. **`ApiEmbedder` 的测试用注入假客户端而不是 `httpx.MockTransport`。**
   仍在零网络条件下断言请求体与解析，只是更贴近 `openai` SDK 的真实调用形状；
   `api` 路线会被 `select_encoder` 显式探测一次维度（一次极短调用），
   避免索引键随首次调用漂移。
6. **多轮范围用 `[scope=...]` 标记承载。** 计划只说"从上一轮继承"，
   实现上把范围写进助手消息的可见标记，既不破坏前端渲染，也不用反解自然语言。
7. **T9 的真实 LLM 冒烟已于 2026-09-12 执行**（用户填入 Key 后）：4 个问题的问答 + 一场真实录音的
