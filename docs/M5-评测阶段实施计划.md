## 执行说明

**Goal**：把「我觉得效果还行」变成「我知道它在哪一档、差在哪、改一个旋钮会差多少」——
建立可复现的评测数据集与指标库，让《产品设计文档》第 8 节的每一项指标都有脚本、有数字、
有前后对比，并把 M3 明确留给 M5 的两件事（cross-encoder 重排、Langfuse 可观测）做完。

**Architecture**：评测与单测彻底分开。单测保证"不坏"（离线、断言行为），评测回答"好不好"
（数据集 + 指标 + 消融）。新增 `app/eval/` 一层纯函数库（数据集装载、指标计算、运行器、
报告渲染），标注集落 `samples/annotations/m5/`，一次运行产出
`data/eval/<run_id>/`（逐条明细 + 汇总指标 + Markdown 报告）。默认运行使用
`MA_LLM_MODE=off` 的确定性基线（无 Key 也能跑出完整报告），真实模型运行作为显式可选项。

**Tech Stack**：Python 3.12 · pytest · SQLite（FTS5）· 本地 BGE（文本向量）·
可选 cross-encoder 重排 · OpenAI 兼容 LLM（DeepSeek）· Langfuse（可自托管，可选降级）·
纯 Markdown/JSON 报告（无前端改动）

**Spec**：本文档即 M5 的 spec 与实施计划，承接《产品设计文档》8 节指标表与《技术方案》
17 节 M5 行，并关闭 M3 决策 ③（重排留 M5）与决策 ⑨（Langfuse 留 M5）。

**MVP 范围说明（2026-09-12 拍板）**：本次只实现本文档的任务 T0–T9 与第 10 节的必答决策，
不做被列为"可选加分项"的内容——LLM 重排对照、幻灯片讲解材料、CI 常驻评测一律不做；
重排只落 cross-encoder 一条路径（决策 ②=A）。

**数据来源说明（决策 ①=B）**：评测语料以**你提供的真实会议录音（脱敏）**为准。
标注骨架与校验逻辑先落地，真实音频与金标到位后按第 11 节第 1 条的流程补入并重跑。
在素材到位前，报告里的数字以仓库现有样例会议为准，并明确标注"数据源=样例"，不冒充真实会议。

## Global Constraints

全程适用，每个任务的要求都隐含包含这一节。

1. **C3 不回退**：`pytest` 必须在无网络、无 GPU、无模型权重、无 API Key 的机器上全绿。
   评测脚本本身也必须有"无 Key 可跑"的确定性基线，否则报告无法被他人复现。
2. **单测与评测分离**：评测用例不进 `tests/`（它们需要完整数据集与更长时间），
   单测只测指标函数的正确性（用构造的假数据，不断言真实效果）。
3. **数字必须可复现**：每个数字都要能由一条命令重跑得到；报告里必须写清数据集版本、
   运行配置（编码器 / 路由模式 / 阈值）、模型名与日期。随机性来自模型时，
   同一次运行内的比较必须用同一份缓存（`cache_first` + `warm_cache.py`）。
4. **标注集不喂给被测系统**：金标只用于比对，不进入检索语料、不进提示词。
   任何"把答案塞进上下文"的评测都算作弊。
5. **指标只报可解释的量**：每个指标要写清分子、分母与判定规则；无法解释的复合分不报。
   效果不好时保留原始逐条明细，便于定位而不是只给一个数字。
6. **成本有上限**：真实模型评测前先跑 `--dry-run` 统计预计调用次数与 token，
   超过 `MA_EVAL_TOKEN_BUDGET` 直接中止并给出差额。
7. **依赖精确锁定**：新依赖（重排模型、Langfuse SDK）装完立刻写回 `requirements.txt`
   （`==`）并刷新 `requirements.lock.txt`；可选依赖单独成文件，保证主路径不受影响。
8. **测试先行**：每个任务先写失败测试再实现，任务收尾时全量 `pytest` 通过。
9. **本地验证命令**（沙箱/CI 里 pytest 默认临时目录可能不可写，用工作区内的目录）：

```powershell
.\meeting_assistant\Scripts\python.exe -m pytest -q --basetemp=.pytest_tmp
.\meeting_assistant\Scripts\python.exe tests\test_docs.py
.\meeting_assistant\Scripts\python.exe scripts\run_eval_all.py --offline
```

10. **密钥不入库**：API Key 与 Langfuse 公钥/私钥只从环境变量或 `.env` 读取，
    不写进代码、不写进文档、不进日志、不入库；`.env.example` 只留空值占位。

## 1. 目标与验收口径

《产品设计文档》8 节给出评测维度的原始口径：

> 纪要质量（Schema 合法率、待办抽取准确率/召回率、关键结论命中率、负责人归属准确率）、
> 证据可靠性（证据正确率）、检索效果（Recall@k、命中排序质量、跨会议检索准确率）、
> 对话行为（意图路由准确率、多轮上下文保持正确率、无答案场景拒答正确率）、
> 成本（单场会议 token 消耗与费用、单次问答 token 与响应耗时）。

M5 的验收口径具体化为 7 条：

1. **每一项指标都有脚本、有数字**：上面 12 个指标一个不缺，全部出现在
   `docs/M5-评测报告.md` 的汇总表里，并且每个数字都能一键重跑。
2. **标注集达到可用规模**：≥ 5 场会议 / ≥ 100 条片段 / ≥ 50 条检索标注 / ≥ 30 条路由标注 /
   ≥ 20 条问答标注 / ≥ 5 场人工纪要金标（规模见决策 ④）。
3. **有消融对比**：至少给出 4 组配置的横向对比（无模型基线、M3 默认、+重排、+人在回路），
   结论必须落到"哪个旋钮值多少分"，而不是"整体感觉更好"。
4. **重排有定论**（M3 决策 ③ 的收口）：cross-encoder 重排做与不做、提升多少 Recall@k / MRR、
   代价多少延迟与内存，给结论并写进《技术方案》9.1。
5. **拒答与编造被单独度量**：域内作答率、域外拒答正确率、证据正确率三项分开报，
   并给出"无证据结论被拦截"的用例证据（C4 的可度量形态）。
6. **成本与延迟可解释**：单场会议、单次问答的 token / 费用 / P95 延迟，以及缓存命中率；
   价格口径写进报告（含未配 Key 时的估算方式）。
7. **可观测落地**（M3 决策 ⑨ 的收口）：Langfuse 记录每次图运行，看板包含路由准确率、
   拒答率、平均 token、P95 延迟、单场成本；服务不可用时降级到本地报告，不影响评测产出。

**建议验收阈值**

| 验收项 | 口径 | 目标值 |
| --- | --- | --- |
| 指标覆盖 | 《产品设计文档》8 节 12 个指标 | **12 / 12** 有数字 |
| 数据集规模 | 会议 / 片段 / 检索 / 路由 / 问答 / 纪要金标 | 5 / ≥100 / ≥50 / ≥30 / ≥20 / ≥5 |
| 检索 | Recall@k（k=8）、MRR | Recall@8 **≥ 0.90**；MRR 不低于 M3 的 0.881 |
| 重排 | 相对 RRF-only 的提升 | MRR 提升 ≥ 3%，P95 延迟增加 ≤ 300 ms |
| 拒答 | 域外拒答正确率、域内作答率 | 拒答 **≥ 0.95**；作答率 **≥ 0.90** |
| 纪要 | Schema 合法率、待办 F1、负责人归属准确率 | Schema **1.000**；F1 **≥ 0.70**；归属 **≥ 0.80** |
| 证据 | 证据正确率（含 LLM 判定与人工抽样） | **≥ 0.90**，人工抽样 ≥ 30 条 |
| 对话行为 | 路由准确率、多轮上下文保持 | 路由 **≥ 0.90**；多轮 **≥ 0.85** |
| 成本 | 单场会议 / 单次问答 | 实测值 + 明码口径；重复提问缓存命中 0 token |
| 可复现 | `scripts/run_eval_all.py --offline` | 一条命令产出报告，无网络依赖 |

阈值是起点：如果实测达不到，报告要说明原因与下一步，而不是调低阈值——阈值修改必须
在报告里留下前后两版数字。

## 4. 架构与文件结构

### 4.1 评测链路

```text
samples/annotations/m5/            ← 数据集（人写、随仓库分发、不喂给被测系统）
  retrieval_gold.json              检索：query → 金标片段 + 是否应拒答
  route_gold.json                  路由：query → 期望 intent / answer_mode / scope
  qa_gold.json                     问答：query → 金标要点（句子级）+ 允许引用的片段集合
  minutes_gold.json                纪要：meeting_id → 待办 / 决议 / 负责人 金标
  review_gold.json                 协同：待确认条目 → 期望处理动作（M4 产物）
        │
        ▼
app/eval/dataset.py               装载 + schema 校验 + 与库内会议对账（金标片段必须存在）
        │
        ▼
app/eval/runner.py                按配置跑：建临时数据目录 → 载入种子/会议 → 逐条执行 → 收集原样输出
        │                         （离线基线 / cache_first / live 三种模式）
        ▼
app/eval/metrics.py               纯函数指标：P/R/F1、命中率、Recall@k、MRR、准确率、拒答、成本、P95
        │
        ▼
app/eval/report.py                渲染 Markdown（汇总表 + 消融矩阵 + 逐条明细 + 局限说明）
        │
        ▼
data/eval/<run_id>/{raw.json, metrics.json, report.md}
docs/M5-评测报告.md                ← 选定 run_id 的报告，随仓库提交（结论 + 数字 + 复现命令）
```

### 4.2 为什么把评测做成一层而不是几个脚本

三个脚本（检索 / 纪要 / 对话）各自加载数据、各自算指标，会出现同一指标两种算法、
同一数据集两种口径。`app/eval/` 把"数据集契约 → 执行 → 指标 → 报告"固定成一条链：
每个指标是纯函数（可单测），每次运行留一份 `raw.json`（可追溯），报告是渲染结果（可重生成）。

## 5. 关键设计

### 5.1 数据集契约

```python
class RetrievalCase(BaseModel):
    query: str
    gold_segments: list[str] = []       # "meeting_id:segment_id"，空表示应拒答
    gold_meetings: list[str] = []       # 跨会议问题：允许命中的会议集合
    note: str = ""

class RouteCase(BaseModel):
    query: str
    intent: Literal["process_audio", "query_content", "query_speaker", "unknown"]
    answer_mode: str                     # structured / content / clarify / refuse
    scope: list[str] = []                # 期望锁定的会议
    context: list[str] = []              # 多轮场景：前置轮次

class QACase(BaseModel):
    query: str
    gold_points: list[str]              # 句子级要点（用于覆盖率判定）
    allowed_segments: list[str]         # 允许引用的片段集合（越界引用算错）
    must_refuse: bool = False
```

四条校验（`dataset.py`，缺一条就报错而不是静默跳过）：

1. **金标片段必须真实存在**：`meeting_id:segment_id` 能在种子库里查到；
2. **应拒答的用例没有金标**，有金标的用例不能标 `must_refuse`；
3. **会议覆盖完整**：每场会议至少有 1 条检索、1 条问答用例（否则该场会议没被评测到）；
4. **数据集有版本号**：文件顶层带 `version` 与 `updated_at`，报告里必须写版本。

### 5.2 指标定义（分子 / 分母写清楚）

| 指标 | 分子 | 分母 | 说明 |
| --- | --- | --- | --- |
| Schema 合法率 | 结构合法的纪要场数 | 总场数 | 含重试后成功；单条降级不算失败，但要单列 |
| 待办抽取准确率 | 与金标匹配的待办数 | 系统产出的待办数 | 匹配规则：事项文本相似度 ≥ 0.75 视为同一条 |
| 待办抽取召回率 | 与金标匹配的待办数 | 金标待办数 | — |
| 关键结论命中率 | 被系统覆盖的金标决议 | 金标决议数 | 覆盖判定：LLM 判定（`judge.py`）或人工 |
| 负责人归属准确率 | 负责人正确的待办数 | 有负责人的待办数 | 只在金标有明确负责人的条目上算 |
| 证据正确率 | 引用被判定支撑结论的条数 | 总引用条数 | 规则版 + LLM 判定版 + 人工抽样 |
| Recall@k | 命中金标片段的查询数 | 有金标的查询数 | k=8；跨会议查询按 `gold_meetings` 判 |
| MRR | Σ(1/首个命中名次) | 有金标的查询数 | 与 M3 报告同口径，便于对比 |
| 跨会议检索准确率 | 只引用到允许会议的查询数 | 跨会议查询数 | 衡量"会不会串会场" |
| 域内作答率 | 有作答的域内查询数 | 域内查询数 | 与拒答是一对：作答率低说明过度拒答 |
| 域外拒答正确率 | 正确拒答的域外查询数 | 域外查询数 | 不调用 LLM 的拒答才算"正确拒答" |
| 路由准确率 | 意图 + 模式 + 范围全对的查询数 | 路由标注数 | 三项分开也报，便于看错在哪 |
| 多轮上下文保持 | 追问轮次中范围继承正确的轮数 | 追问轮数 | 用 `route_gold.json` 的 `context` 构造多轮 |
| 单场会议成本 | Σ token / 费用 | 场数 | 从 `chat_traces` + 纪要链路记录汇总 |
| 单次问答成本 | Σ token / 费用 | 问答数 | 缓存命中单列 |
| P95 延迟 | 第 95 百分位耗时 | — | 新增 `chat_traces.latency_ms` |

### 5.3 可复现运行：三种模式

| 模式 | 开关 | 用途 | 依赖 |
| --- | --- | --- | --- |
| 离线基线 | `--offline`（`MA_LLM_MODE=off` + 编码器 auto） | 每次都跑，作为回归基线与无 Key 机器的完整报告 | 无 |
| 缓存优先 | `--cache-first` | 报告里的真实模型数字（同一份缓存保证可比较） | 需要预热过的缓存 |
| 真实在线 | `--live` | 首次生成缓存、成本实测 | 需要 Key 与预算 |

同一份报告里不同配置的对比必须来自同一模式；跨模式比较要显式标注（否则"缓存版 vs 在线版"
的差异会被误读成效果差异）。

### 5.4 重排消融（关闭 M3 决策 ③）

```python
class Reranker(Protocol):
    name: str
    def rerank(self, query: str, candidates: list[Retrieved], *, top_k: int) -> list[Retrieved]: ...

class NoReranker:            # 默认：直接返回 RRF 顺序
class CrossEncoderReranker:  # 本地 bge-reranker-base，懒加载，失败回落 NoReranker
class LLMReranker:           # 用现有 LLMClient 对 top-N 打相关性分（可选，用于对比）
```

消融表固定三行（可再加 top-N 扫描）：

| 配置 | Recall@8 | MRR | 域外拒答 | P95 延迟 | 峰值内存 |
| --- | --- | --- | --- | --- | --- |
| RRF-only（M3 默认） | — | — | — | — | — |
| + cross-encoder（top-20 → top-8） | — | — | — | — | — |
| + LLM 重排（top-20 → top-8） | — | — | — | — | — |

结论落点：如果重排带来的 MRR 提升不足 3%，或者延迟增加超过 300 ms，就**保留 RRF-only
作为默认**，把重排写成"已验证但默认关闭的可选路径"——这本身也是一个可讲的工程判断。

### 5.5 证据正确率：规则 + LLM + 人工抽样

```text
规则版（默认，零成本）：引用片段存在 + 结论与片段的关键词覆盖率 ≥ 阈值
LLM 判定版（judge.py）：把「结论 + 引用片段」成对喂给模型，输出 supported / unsupported
人工抽样（校准）：从 LLM 判定为 positive / negative 的两类中各抽 15 条人工复核
```

三者关系写进报告：规则版的假阳性率、LLM 判定与人工的一致率（Cohen's kappa）。
这一步是把 M3 的"证据校验"从工程约束升级为可度量的质量指标。

### 5.6 成本与延迟口径

* **token 计数**：沿用 M3 的字符数估算（中文 ≈ 字符数），报告里明写这是估算口径；
  若模型返回真实 usage，以真实值为准（`llm_cache` 已存 token）。
* **价格**：优先 `MA_LLM_PRICE_INPUT/OUTPUT`；未配置时用内置价目表；都没有的模型按 0 计
  并标注"未计价"，**不编数字**。
* **单场会议成本**：纪要链路（map-reduce 多次调用）+ 该场会议的问答汇总；
  为此给 `chat_traces` 补 `meeting_id`（可空列，随迁移 v5 一起加）。
* **延迟**：节点耗时求和写入 `latency_ms`；P95 只用同一次运行、同一模式的数据，不跨模式混算。

### 5.7 可观测：Langfuse 与降级

```python
class TraceSink(Protocol):
    def record(self, *, name: str, thread_id: str, nodes: list[TraceStep], usage: dict, cost: float) -> None: ...

class NullTraceSink:       # 默认：什么都不做（离线与 CI 路径）
class LangfuseTraceSink:   # 有 Key 且可连通时启用；失败只记日志，不影响主流程
```

接入原则：**`chat_traces` 仍是唯一事实源**（评测报告从它算），Langfuse 是展示层。
这样即使现场没有 Docker、没有网络，报告照常产出。

### 5.8 报告结构（`docs/M5-评测报告.md`）

1. 评测口径（数据集版本、运行配置、模型名、日期、复现命令）
2. 数据集规模与覆盖（每场会议的用例数）
3. 指标汇总表（12 项）
4. 消融矩阵（无模型基线 / M3 默认 / +重排 / +人在回路）
5. 分项明细（检索逐条、纪要逐场、对话逐条）
6. 成本与延迟
7. 局限与下一步（哪些结论样本量不够、哪些指标靠 LLM 判定）

## 12. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 标注量不足导致检索指标饱和（M3 已出现 Recall@8 = 1.000） | 指标无区分度，说不出结论 | 扩标注时刻意加入改述、跨会议、多跳问题；报告里如实保留"饱和"这个事实并说明样本量 |
| 金标质量不高 | 所有下游结论都不可信 | 匹配规则写死且可解释；人工抽样校准；报告标注"金标由谁在何时确认" |
| 真实模型不可复现（同问不同答） | 数字无法对比 | 同一份报告内的比较统一走 `cache_first`；`--live` 只用于首次生成缓存与成本实测 |

| LLM 判定与人工不一致 | 证据正确率可信度低 | 报告同时给规则版、LLM 版与人工抽样三点，并给一致率 |
| 重排模型拖慢链路或占内存 | 演示时卡顿 | 结论门槛写死（MRR +3% / 延迟 +300 ms）；不达标就默认关闭并如实写进报告 |
| Langfuse 服务不可用 | 演示中断 | `TraceSink` 降级为 `NullTraceSink`；报告不依赖 Langfuse |
| 评测脚本本身有 bug | 数字错但看起来正常 | 指标纯函数 + 手算对照单测；关键指标用两组独立构造数据交叉验证 |

### 16.3 与计划的显式偏差

1. **纪要在离线运行下标注为"占位数字"**：计划只说要跑指标，实现时发现模型关闭时
   纪要回落到固定备用内容，若直接报数字会给人"质量已验证"的错觉，
   因此在 metrics 里加 `offline_placeholder` 并在报告顶部注明。
2. **跨会议准确率用会议粒度而不是片段粒度**：相邻片段（±1 窗口）是检索层刻意拼进来的，
   用"片段必须在金标列表里"去卡会把正确的邻接引用误判为错误。
3. **重排默认值保持 `off`**：实测 MRR +13.6% 达到升级门槛，但默认引入 1.1 GB 权重
   会破坏"克隆即可跑"的基线，因此作为实测有效的可选项保留。
4. **未测真实模型与 Langfuse 服务端**：两者都需要外部条件（Key / Docker），
   报告第 7 节如实标注为待跑，并给出跑法与预算预演命令。
5. **标注集规模未达决策 ④（3/5 场）**：真实会议录音由用户提供，属决策 ①=B 的待办；
