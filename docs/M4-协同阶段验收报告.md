## 2. 挂起与恢复

### 2.1 图结构

```text
START → generate → validate
           ├─(非法 且 retry < 2)→ generate
           └─(合法)→ review_gate
                       ├─(有待确认条目)→ interrupt(载荷) → 线程结束，检查点落盘
                       └─(无)→ finalize → END
恢复：POST /api/review/{id}/resolve → 写 override + 审计 → 待确认为空时
      Command(resume=…) → review_gate 重入 → finalize → 会议 processed
```

### 2.2 三个关键工程决定（都有用例守着）

1. **落库在闸门之前。** `generate` 节点先写会议、片段与纪要，`review_gate` 只读状态。
   这样挂起期间待确认区读得到数据；顺序反过来会读到空纪要、算出 0 条待确认
   （实现时踩过一次，`test_pending_items_suspend_and_stay_queryable` 守住这条）。
2. **闸门节点零副作用。** `interrupt` 恢复时框架会重新执行包含它的节点，
   因此闸门只做判断与挂起，LLM 调用在它上游的 `generate` 里——恢复不会重复花钱。
3. **恢复有降级路径。** 恢复判据只用业务库（`minutes` + `override`），
   检查点只决定"能否复用图"。检查点库被删、换机器、`MA_CHECKPOINT_BACKEND=off` 时
   确认接口照样把会议收尾，不返回 5xx。

### 2.3 检查点

| 项 | 实现 |
| --- | --- |
| 后端 | `MA_CHECKPOINT_BACKEND = sqlite（默认）| memory | off` |
| 位置 | `<data_dir>/checkpoints.sqlite`（与业务库分开，框架 schema 与业务 schema 不混） |
| thread | chat 图 = `conversation_id`；minutes 图 = `meeting_id` |
| 序列化 | 显式登记领域模型白名单（`Meeting` / `Segment` / `Minutes` 等），避免未来版本拒绝反序列化 |
| 分层 | 只有 `app/agent/graph.py` 与 `app/agent/checkpoint.py` import LangGraph，静态用例守住 |

## 3. 待确认区与人工动作

* **口径唯一**：`app/store/minutes_repo.py::pending_items` 是待确认清单的唯一实现，
  会议列表的 `review_count`、会议详情的 `review_items`、编排层的闸门判据都调它；
* **覆盖范围**（决策 ②=A）：待办（`needs_review`）+ 置信度低于 `MA_REVIEW_CONFIDENCE`
  （默认 0.75，与 `ActionItem` 的既有阈值统一）的决议；
* **动作**：`confirm` / `dismiss` / `edit`（改派负责人、改截止时间）；决议不可编辑；
* **审计**：每次动作写一条 `review_events`（动作、改前改后、时间），
  `GET /api/review/{item_id}/events` 可查；M5 的人工介入率与驳回率直接取自这张表；
* **幂等**：重复确认同一条返回 200，不重复写审计（前端双击 / 重试安全）。

## 5. 状态机与事件

```text
meetings.status:  processing → awaiting_review → processed
                        └────────(无待确认条目)────────┘
tasks:            queued → running → done（备注写明"含 N 条待确认条目"）
SSE:              stage → review（新增）→ result → done
```

* `review` 事件在任务收尾且存在待确认条目时推送（含 `meeting_id` / `count` / `items`），
  前端收到后提示并切到待确认区；
* 既有 `stage` / `result` / `done` / `error` 载荷未改动（契约用例继续全绿）；
* 重新生成纪要后状态会重新计算（`POST /api/meetings/{id}/minutes/regenerate`）。

## 7. 与计划的显式偏差

1. **任务阶段没有追加"等待人工确认"。** 计划 5.5 节写的是把该阶段加到 `tasks.stages` 末尾、
   进度停在 90%。实现里改为在任务 `notes` 写明"含 N 条待确认条目"，
   因为 `stages` 是感知层的阶段列表（由 `get_stages()` 生成），
   往里塞一个编排阶段的代价是让"任务进度"与"感知流水线"两个概念错位。
   前端体验不变（SSE 会推 `review` 事件、待确认区有徽标）。
2. **`ReviewItem` 没有加 `title` / `detail` / `payload` 三个字段。**
   计划列了它们，实现只加了 `kind` / `editable` / `due`：待办与决议的正文共用既有 `task`
   字段（前端渲染逻辑不用改两套），`payload` 属于"前端不应依赖的内部结构"，不加更好。
3. **决议阈值统一为 0.75。** 计划写的是 `MA_REVIEW_CONFIDENCE=0.70`，
   实现时发现 `domain/models.py` 里 `ActionItem` 的既有阈值是 0.75，
   两个数并存会让"为什么这条待办进待确认、那条决议不进"讲不清，因此统一为 0.75。
4. **检查点序列化显式白名单。** 计划只写"接 `SqliteSaver`"，实现时 LangGraph 对
   未登记类型会告警并预告未来版本拒绝反序列化，因此在 `checkpoint.py` 里显式登记领域模型。
5. **重新生成纪要也会刷新状态。** 计划只在音频任务路径上定义了状态机；
   实现发现 `regenerate` 同样可能产出低置信度条目，若不刷新就会出现
   "会议是 processed、却带着 3 条待确认"的矛盾状态。
6. **`openSegment` 从同步改为 async。** 跨会议跳转需要先 `await loadLibrary()`，
   调用方（`app.js` 的点击处理）不关心返回值，改动对外无影响。

| 限制 | 影响 | 下一步 |

| 低置信度片段不能人工改派发言人 | 声纹归属错误只能忽略，不能纠正 | M5 之后作为可选能力（M4 决策 ②=B） |
