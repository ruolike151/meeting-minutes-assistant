## 3. 总体架构

```text
浏览器（原生 HTML / CSS / JS，三栏布局）
  对话区 · 会议库侧栏 · 详情面板（纪要 / 原声 / 待确认 / 待办）
        │ REST + SSE
FastAPI（app/main.py）
  路由：chat / meetings / review / export / audio
        │
编排层 LangGraph（app/agent）
  意图路由 → 三条路径 → 澄清 / 拒答 / 人在回路
        │
   ┌────┴─────┬──────────┐
工具层        检索层       感知层
tools/       retrieval/   perception/
   └────┬─────┴──────────┘
基础设施：LLM 适配 · SQLite · 文件目录 · Langfuse
```

分层规则：

1. 依赖只向下。编排层可调用工具、检索、感知；反向引用一律禁止。
2. 工具层与感知层不 import 编排框架，对外只暴露 Pydantic 模型。
3. 模型访问只经 `LLMClient` 协议，便于替换供应商与打桩。
4. 前端不持有业务规则。意图路由、检索、拒答全部在后端，前端只负责渲染与交互。

## 4. 技术选型与理由

### 4.1 编排：LangGraph

约束 C1、C2、C6 一起把编排方案锁死了：需要有状态、有分支、能中断、能单独测试。

LangGraph 提供的正是这四件事——`StateGraph` 承载会话状态，条件边表达意图路由，
checkpointer 让长任务与多轮对话可恢复，`interrupt` 让待确认区可以挂起等待人工处理。
节点是普通函数，因此"这句话该走哪条路"可以在测试里直接断言。

代价也要说清楚：学习曲线、版本漂移、简单流程会被写得比实际复杂。缓解办法是把
图的用途严格限制在编排层——图只回答"什么时候调用谁"，节点内部的逻辑全部写成不依赖
框架的纯函数。这样框架出问题时的爆炸半径可控。

**为什么不用 LangChain 的 `AgentExecutor`。** 它的 ReAct 循环是不透明的：prompt 由
框架拼接，重试与解析错误难以拦截，路由结果无法在测试中断言，直接冲突于 C1。用三行
代码跑通一个 Agent 在面试里也不加分，因为讲不出控制点在哪。

**为什么不用完全自研的 Agent Loop。** 对一条线性链路，自研更简单。但本项目要的是
状态持久化、中断恢复、带条件重试的边、流式进度，这些写下来就是重造一遍 LangGraph。
自研烧掉的时间正好该花在检索层上，而产品文档 5.4 节明确指出检索是这个项目技术含量
最高的部分。这是资源错配。

### 4.2 组件：只取 LangChain 的零件

依赖 `langgraph` 与 `langchain-core`，不引入 `langchain` 的 chains / agents 高层封装。

实际使用的部分：`ChatOpenAI`（`base_url` 指向任意 OpenAI 兼容端点，满足"切换供应商
不改上层代码"）、消息类型、工具契约。不使用：`AgentExecutor`、内置 memory 模块、
预置 chain。

这样做的收益是供应商切换只改一处配置，同时避免了高层封装把 prompt 与循环藏起来。

### 4.3 检索：自研混合检索

不用 LlamaIndex，理由与 4.1 同源：这一层是本项目的技术差异点，也是最容易被追问的
地方。索引粒度、过滤顺序、RRF 融合、重排、拒答阈值都需要逐项调参并用标注集量化，
包进框架后就失去了调优与讲解的抓手。

规模上也不需要专用向量库：MVP 是 3–5 场会议、几百到几千个片段，numpy 暴力余弦
在毫秒级完成。向量持久化为 SQLite BLOB，检索层对外只暴露 `VectorIndex` 协议，
将来换 sqlite-vec 或 faiss 不影响上层。

### 4.4 前端：FastAPI + 轻前端

三个候选：Streamlit、React / Vue、原生前端 + FastAPI。

Streamlit 被否决的原因是具体的——它无法表达原型已经定型的三栏布局与证据回跳，
每次交互重跑整个脚本的模型也和 SSE 流式进度不契合，而界面降级会让原型阶段的
工作白做（冲突于 C7）。React / Vue 能做，但要引入构建链路，对一个单人项目属于
过度投入。

选定方案：FastAPI 同时提供 API 与静态资源，前端为无构建的原生页面。原型里
`app.js` 已经用同样的方式实现了路由、渲染与导出，正式版基本是"移植 + 接后端"，
而不是重写。

代价是状态管理要手写。缓解办法是刻意保持状态极小：一个 store 对象加若干渲染函数，
不引入虚拟 DOM 与响应式系统。

### 4.5 否决记录

| 方案 | 否决原因 |
| --- | --- |
| LangChain `AgentExecutor` | 循环不透明，路由不可断言，与 C1 冲突 |
| 完全自研 Agent Loop | 要重写状态持久化与中断恢复，时间应从检索层出 |
| LlamaIndex 托管检索 | 把项目的技术差异点藏进框架，无法逐项调参讲解 |
| Streamlit | 表达不了已定型的界面，与 C7 冲突 |
| 专用向量数据库 | MVP 规模用不上，numpy 已在毫秒级 |
| 前端框架 + 构建链路 | 单人项目收益不足，成本落在构建与状态管理上 |

## 6. 数据契约与存储

### 6.1 领域模型

用 Pydantic 定义，同时承担三件事：LLM 结构化输出的目标 schema、入库前的校验、
接口的序列化格式。

```python
class Segment(BaseModel):
    id: str
    meeting_id: str
    start: float
    end: float
    speaker_id: str | None
    speaker_confidence: float
    text: str

class ActionItem(BaseModel):
    id: str
    task: str
    owner: str | None
    owner_source: Literal["explicit", "inferred", "unknown"]
    due: date | None
    status: Literal["pending", "done", "cancelled"]
    evidence: list[str]          # 片段 ID，C4 的载体
    confidence: float
    needs_review: bool
```

`evidence` 为空或置信度低于阈值时，`needs_review` 置真——条目不进最终稿，
先落到待确认区。

### 6.2 表结构

```sql
meetings(id PK, title, date, duration, status, created_at)
participants(meeting_id, speaker_id, name, speaking_seconds, embedding BLOB)
segments(id PK, meeting_id, start, end, speaker_id, speaker_confidence, text, text_tokens)
segments_fts USING fts5(text_tokens, content='segments', content_rowid='rowid')
minutes(meeting_id PK, payload JSON, schema_version, updated_at)
conversations(id PK, created_at)
messages(id PK, conversation_id, role, content, evidence JSON, created_at)
action_item_overrides(id PK, meeting_id, item_id, status, owner, due, updated_at)
llm_cache(prompt_hash PK, model, response, input_tokens, output_tokens, cost, created_at)
```

两点说明：

**中文全文检索。** FTS5 的 `unicode61` 分词器不切分中日韩文字，直接索引中文原文
会导致整句成为一个 token。做法是入库时用 jieba 预分词，把空格分隔的结果写入
`text_tokens`，FTS5 对该列建索引。人名与专有名词加入用户词典，避免被切碎。

**人工修改单独存表。** 用户确认待办状态或负责人后写入 `action_item_overrides`，
重新生成纪要时以 override 为准。否则一次重算就会把人工确认的结果覆盖掉。

## 7. 编排层设计

### 7.1 状态定义

```python
class AgentState(TypedDict, total=False):
    thread_id: str                  # = conversation_id，checkpointer 的键
    user_input: str
    attachments: list[Attachment]   # 音频
    history: list[Message]          # 压缩后的会话上下文
    intent: Intent                  # process_audio | query_content | query_speaker | unknown
    scope: Scope                    # 会议范围：全体 / 单场 / 未定
    evidence: list[Segment]
    draft: Minutes | None
    answer: str
    citations: list[str]
    clarify_question: str
    review_items: list[ActionItem]
    retry_count: int
    trace: list[ToolCallRecord]
    usage: Usage
```

### 7.2 图结构

```text
START → route
  ├─ process_audio
  │     normalize → transcribe → identify_speakers → index_segments
  │       → generate_minutes → validate
  │            ├─(schema 不合法 且 retry < 2)→ generate_minutes
  │            └─(合法)→ review_gate
  │                        ├─(存在待确认条目)→ interrupt 挂起，等待人工确认
  │                        └─(无)→ finalize → END
  ├─ query_content
  │     resolve_scope
  │       ├─(范围不唯一)→ clarify → END
  │       └─(已确定)→ retrieve → grade
  │                          ├─(低于阈值)→ refuse → END
  │                          └─(命中)→ synthesize → verify_evidence
  │                                        ├─(证据不足)→ 降级为待确认 / refuse
  │                                        └─(通过)→ finalize → END
  ├─ query_speaker → aggregate_by_speaker → synthesize → verify_evidence → finalize → END
  └─ unknown → clarify → END
```

### 7.3 节点职责

| 节点 | 职责 | 调用模型 | 测试方式 |
| --- | --- | --- | --- |
| `route` | 判定意图与查询范围 | 是（结构化输出 + 规则兜底） | FakeLLM 断言路由结果 |
| `resolve_scope` | 确定会议范围，会话已有当前会议则直接沿用 | 否 | 纯函数断言 |
| `clarify` | 信息不足时反问，不做猜测 | 否（模板） | 断言澄清问题文案 |
| `transcribe` / `identify_speakers` | 感知层，offline 后端可替换 | 否 | 固定样例 |
| `generate_minutes` | 分段 map-reduce 生成结构化纪要 | 是 | FakeLLM 返回固定 JSON |
| `validate` | Pydantic 校验，失败带错误重试 | 否 | 构造非法 JSON 触发重试路径 |
| `retrieve` | 调用检索层，产出证据片段 | 否（内部用 embedding） | 固定片段集断言召回 |
| `grade` | 判断证据是否足以回答 | 否（阈值） | 断言阈值边界 |
| `synthesize` | 基于证据生成回答，输出引用标记 | 是 | FakeLLM 断言引用透传 |
| `verify_evidence` | 校验每条结论是否被引用片段支撑（C4） | 是（可选规则） | 构造无支撑结论，断言被拦截 |
| `refuse` | 无证据时的明确答复 | 否 | 断言不编造 |
| `review_gate` | 低置信度条目挂起，等人工确认 | 否 | 断言 interrupt 触发与恢复 |

### 7.4 三个关键机制

**多轮上下文。** 最近 N 轮保留原文，更早的轮次压缩为摘要后进入 `history`，
避免上下文随轮次线性增长。`scope` 随会话保存，"我说的是哪场会"这类信息只问一次。

**拒答先于生成。** `grade` 节点在调用 LLM 之前判断证据是否达标，不达标直接走
`refuse`。这比"让模型自己说不知道"可靠得多，也是产品文档 9 节"拒答正确率"的来源。

**证据校验后置。** 生成完不是直接返回，而是把每条结论与它引用的片段再做一次
支撑性判定，不通过的条目录入待确认区。这一步是把"带引用"从展示格式变成质量约束。

## 8. 工具层设计

## 9. 检索层设计

### 9.1 流水线

```text
query
 ① 过滤    按 scope 收窄：meeting_ids / speaker_ids / 时间范围
 ② 关键词   query 先分词，FTS5 BM25 召回 top-K1
 ③ 向量     查询向量 → 候选集内暴力余弦召回 top-K2
 ④ 融合     RRF：score = Σ 1 / (k + rank_i)，k = 60
 ⑤ 阈值     融合分低于 τ 的候选直接丢弃
 ⑥ 重排     cross-encoder 对 top-N 精排，取 top-k
 ⑦ 组装     命中片段 + 相邻片段（±1），按 token 预算裁剪，按时间排序
 ⑧ 拒答     最终最高分低于 τ' 时不调用 LLM，直接返回"未找到"
```

初始参数：K1 = K2 = 50，RRF k = 60，top-k = 8，相邻窗口 ±1。τ 与 τ' 用标注集
扫出来，不拍脑袋。

**实现口径（M3 落地后的两条修正，实测见 `docs/M3-编排与检索评测报告.md`）：**

1. **RRF 分不作绝对阈值。** RRF 只用排名计算，`1/(60+1)` 这类分值没有跨查询可比性，
   用它卡阈值等于按"被几个召回列表命中"判相关性。因此第 ⑤ 步改用两个可解释量：
   **向量余弦 top1** 与**查询词覆盖率**；RRF 只负责融合排序。
2. **两个信号是"或"的关系，不是"与"。** 任一达标即可作答，两个都不达标才拒答——
   否则"用户换个说法提问"这种本可以靠语义救回来的场景会被覆盖率一票否掉。
   默认阈值：覆盖率 0.34、余弦 0.50（初始值 0.35 在标注集上偏松，域外拒答正确率只有 0.25）。

### 9.2 设计要点

**为什么先过滤。** 会议库会持续增长，先把范围收窄再检索，既降低计算量也提升精度，
并且让"这场会"这类限定语变成确定性的过滤条件而不是靠语义碰运气。

**为什么用 RRF。** 关键词分数（BM25）与向量分数（余弦相似度）量纲不可比，加权求和
需要对分数做归一化，而归一化在不同查询上并不稳定。RRF 只用排名，天然免疫这个问题，
实现也简单。

**中文分词是必需品而非优化。** 见 6.2 节的说明。分词质量直接影响人名、专有名词的
召回，因此用户词典要支持随会议参与者动态添加。

**时间表达式单独处理。**"上周""这周""三月份"先解析成日期区间，再作为过滤条件下推，
而不是交给向量检索去猜。

**相邻片段窗口。** 单条转写片段常常语义不完整（"那这个就下周三之前给"），拼接
相邻片段能显著提升合成质量，代价是 token 预算要相应收紧。

### 9.3 评测

固定标注集上计算 Recall@k、MRR、跨会议检索准确率、拒答正确率。参数（K1、K2、τ、
τ'）以指标为准调整，改动需在评测报告里体现前后对比。

## 10. LLM 适配与结构化输出

### 10.1 适配协议

```python
class LLMClient(Protocol):
    def complete(
        self,
        messages: list[Message],
        *,
        model: str,
        temperature: float = 0.0,
        response_model: type[BaseModel] | None = None,
    ) -> LLMResult: ...
```

三个实现：`OpenAICompatClient`（供应商由 `base_url` + `model` 决定）、
`FakeLLMClient`（按调用序号返回预设响应，供测试）、`CachedLLMClient`（装饰器，
命中缓存直接返回并计 0 成本）。

M3 落地补充：

* **`MA_LLM_PROVIDER=openai` 是协议名而不是厂商名**：换厂商只改 `.env` 里的
  `base_url` + 模型名，代码一行不动；`openai_compat.py` 是全项目唯一 import `openai` 的地方；
* **Key 走 `.env`**（`.gitignore` 已排除，仓库只提交 `.env.example`）：不写进代码、不进日志、不入库；
* **`MA_LLM_MODE = auto | live | cache_first | off`，默认 `auto`**：有 Key 等价 `live`，
  没有 Key 等价 `off`——新克隆的机器不会误发请求，约束 C3 与"无 Key 可跑全部测试"同时成立；
* **`CachedLLMClient` 同时负责记账**：缓存命中计 0，token 与费用累加到 `chat_traces`；
* 结构化输出的 `response_format` 按供应商能力选择（`json_schema` / `json_object` / `prompt`），
  由 `MA_LLM_STRUCTURED_MODE` 配置，降级顺序见 10.2。

### 10.2 结构化输出的降级策略

优先级从高到低：

1. 供应商支持 `json_schema` 时直接约束 schema；
2. 只支持 JSON 模式时，提示词内嵌 schema 并在解析后做 Pydantic 校验；
3. 校验失败时把 `ValidationError` 原文回填，重试最多 2 次；
4. 仍失败则该条目标记为待确认，不让整场会议失败。

第 4 条是关键：单条待办解析失败不应该导致一次会议处理整体不可用。降级而非崩溃。

### 10.3 成本控制

四层：缓存相同请求；限制上下文预算；长会议按主题分段 map-reduce；路由这类低难度
决策可以用小模型或规则完成。成本在 `CachedLLMClient` 处统一累加，落到
`llm_cache` 表，页面可展示单场会议花费。

## 12. 前端设计

- 无构建：`web/` 下 `index.html`、`styles.css`、`app.js`，由 FastAPI 直接托管。
- 三栏沿用原型：左侧会议库、中间对话流、右侧详情面板（纪要 / 原声 / 待确认 / 待办）。
- 设计令牌、深色主题、`prefers-reduced-motion` 全部继承 `styles.css`，不做二次设计。
- 状态管理：单个 store 对象 + 渲染函数，不引入响应式框架。
- 流式：`EventSource` 订阅 `/api/chat`，按事件类型渲染阶段进度与增量文本。
- 证据回跳：沿用原型约定的 `data-mid` / `data-sid` 属性，点击引用 chip 后右侧切到
  "原声"并定位高亮。

与原型中三个模拟函数的对应关系：

| 原型函数 | 正式版 |
| --- | --- |
| `buildAnswer()` | `POST /api/chat`（LangGraph 状态图完成意图路由与工具编排） |
| `processAudio()` | `POST /api/audio` + `GET /api/tasks/{id}/events`（SSE 展示阶段进度） |
| `searchSegments()` | 后端检索层，前端不再本地检索 |

## 13. 可观测与成本

- Langfuse 记录每次图运行：节点耗时、工具调用链、token、单次成本。
- 每次回答落库一条 trace：`conversation_id`、意图、命中片段、引用、耗时、token。
  它同时是调试依据与评测数据来源。
- 关键看板：意图路由准确率、拒答率、平均 token / 问、P95 延迟、单场会议成本。

可观测不是装饰：C1（路由可断言）与拒答正确率这两个指标，都需要 trace 才能被持续
观测，而不是只在评测脚本里跑一次。

## 16. 风险与权衡

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| LangGraph 版本漂移 | 编排层 API 变更导致返工 | 精确锁版本；图只做编排，节点是纯函数 |
| 中文分词质量 | 人名与专名召回差 | jieba 预分词 + 随参会人动态更新的用户词典 |
| 向量规模增长 | 暴力检索变慢 | 先暴露 `VectorIndex` 协议，超阈值再换 sqlite-vec / faiss |
| 结构化输出不稳定 | 纪要缺条目 | 修复重试 + 单条降级到待确认区 |
| 模型成本 | 单场会议费用偏高 | 缓存、上下文预算、分段处理、低难度决策用小模型 |
| 手工状态管理 | 前端代码膨胀 | 状态最小化 + 单一 store，参考原型已有的实现规模 |
| 隐私 | 音频与转写外发第三方 | 页面明确提示，提供本地转写选项（见产品文档待确认事项） |
