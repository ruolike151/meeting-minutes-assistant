## 1. 一分钟版本（开场就用这段）

**一句话**：输入可以是音频，也可以是问题；**输出的每条结论都能一键回到原话核对**。

**它解决什么问题**：会后没人愿意重听录音；AI 摘要又没人敢直接信；
待办散落在各人口头承诺里。这个项目把"录音 → 结构化纪要 → 可检索、可追溯、可追问"做成一条闭环，
并且在**证据不足时明确说"没找到"，不编**。

**技术上最值得说的三件事**：

1. **编排显式化**：LangGraph 状态图管"什么时候调用谁"，节点全是纯函数，
   意图路由可断言、可单测——这是 Agent 工程和"套壳"的分界线。
2. **人在回路真的会停**：低置信度条目不进最终稿，`interrupt` 挂起、检查点落盘、
   人工确认后 `Command(resume=…)` 恢复并收尾；人工改过的结论不会被重算覆盖。
3. **质量可量化**：自研混合检索 + 12 项评测指标 + 消融矩阵，
   能说清"改了哪个旋钮、哪项指标动了几分"，而不是"感觉更好了"。

**兜底能力**：没有 GPU、没有模型权重、没有 API Key、没有网络，也能启动、跑通全流程、跑完 382 项测试
（自动回落到"规则路由 + 混合检索 + 模板装配"）。

## 2. 15 分钟版本：按这个顺序讲

### 2.1 问题与产品形态（1 分钟）

三类典型场景（都来自《产品设计文档》第 2 节）：

| 场景 | 输入 | 输出 |
| --- | --- | --- |
| 会后即时整理 | 上传会议音频 | 结构化纪要 + 待办清单 |
| 历史信息回查 | "上次评审会关于登录改版是怎么定的" | 带原文引用的回答 |
| 发言人维度追踪 | "李工承诺了哪些事" | 按人汇总的发言与待办 |

**对话是唯一入口**，音频只是对话里的一种输入——避免做成"处理工具 + 问答工具"两套入口。

### 2.2 架构：四层，依赖只向下（2 分钟）

```text
浏览器（原生 HTML/CSS/JS，三栏）  —— REST + SSE
        │
FastAPI（app/main.py）—— 路由：chat / meetings / review / export / audio
        │
编排层 app/agent/ —— LangGraph 状态图 + 节点（纯函数）+ 提示词
        │
  ┌─────┴──────┬───────────┐
工具层 tools/  检索层 retrieval/  感知层 perception/
  └─────┬──────┴───────────┘
基础设施：LLM 适配（OpenAI 兼容）· SQLite · 文件目录 · 可选 Langfuse
```

四条分层纪律，每条都有测试守着：

1. **依赖只向下**：编排层可以调用工具/检索/感知，反向引用一律禁止；
2. **只有 `graph.py` 与 `checkpoint.py` import LangGraph**，节点层不依赖框架（静态断言守）；
3. **模型访问只经 `LLMClient` 协议**（真实 / 缓存 / 假实现三态）；
4. **前端不持有业务规则**：路由、检索、拒答全在后端，前端只渲染。

### 2.3 三条链路（5 分钟，这是重点）

#### 链路 A：上传音频 → 结构化纪要

```text
POST /api/audio → 落盘 + 建任务行 + 提交后台 worker（立刻返回 task_id）
GET  /api/tasks/{id}/events → SSE 只轮询任务行，断线重连不影响处理
worker：音频标准化 → 转写(faster-whisper) → 声纹匹配(ECAPA) → 身份对齐 → 片段入库
        → minutes 图：生成（map-reduce）→ 校验 → 人工闸门 → 收尾
```

三个设计点：

* **长会议 map-reduce**：按字符预算分段抽取，再合并；单段失败只丢这一段并记账，不让整场会议失败；
* **结构化输出四级降级**：`json_schema` → `json_object` → 提示词内嵌 schema → 校验失败带错误重试（最多 2 次）；
  仍失败则单条降级到待确认区；
* **单条降级 ≠ 整场失败**：无证据 / 负责人不明 / 无截止时间的条目自动进待确认区。

#### 链路 B：提问 → 带引用的回答

```text
route（意图 + 范围）→ 结构化问题直接读纪要；内容问题走检索
resolve_scope → 未唯一则反问（不猜"你指的是哪场会"）
retrieve → grade（不够就拒答，不调模型）→ synthesize（基于证据写）→ verify_evidence → finalize
```

检索流水线八步（《技术方案》9.1）：

```text
① 过滤（会议/发言人/时间区间，条件全部下推到 SQL）
② 关键词 FTS5 BM25 召回 top-K1
③ 向量召回（本地 BGE / 云端 API / 哈希兜底三档）
④ RRF 融合（只用排名，免疫量纲差异）
⑤ 阈值：查询词覆盖率与向量余弦 top1 —— 任一达标即作答，两个都不达标才拒答
⑥ 重排（M5 实测有效，默认关闭）
⑦ 组装：命中片段 + 相邻片段（±1），按 token 预算裁剪
⑧ 拒答：在调用模型之前完成，不把"是否知道"交给模型自觉
```

两个容易被追问的点，先答掉：

* **为什么 RRF 不做绝对阈值**：RRF 分只编码排名，`1/(60+1)` 这类值没有跨查询可比性；
  真正卡阈值的是"查询词覆盖率"和"向量余弦 top1"两个可解释量。
* **为什么两个信号是"或"关系**：用户换个说法提问时字面覆盖率必然低，语义能救回来；
  用"与"会把它一票否掉（M3 实测：改成"或"之后域外拒答正确率 0.25 → 1.00）。

#### 链路 C：人在回路

```text
会议有待确认条目 → minutes 图在 review_gate 挂起（interrupt）
                  → 状态落 SqliteSaver，worker 线程正常结束（不占资源、不等人工）
用户确认 / 修改 / 忽略 → 写 action_item_overrides + review_events 审计
                     → 待确认为空时 Command(resume=…) 恢复图 → finalize → 会议转 processed
```

三个关键取舍：

* **落库在闸门之前**：挂起期间界面要能读到纪要，所以生成节点先写库；
* **闸门节点零副作用**：`interrupt` 恢复时会重跑包含它的节点，闸门只判断不调模型，避免重复花钱；
* **恢复有降级**：判据只用业务库，检查点丢失 / `MA_CHECKPOINT_BACKEND=off` 时照样能收尾，接口不 5xx。

### 2.4 技术选型与"为什么不是另一个"（3 分钟）

| 选型 | 为什么是它 | 否决了什么，为什么 |
| --- | --- | --- |
| **LangGraph** 编排 | 需要状态、分支、可中断、可单测；节点是纯函数，框架出问题炸不到业务 | LangChain `AgentExecutor`：ReAct 循环不透明，路由无法断言；完全自研：等于重造一遍 LangGraph，时间应从检索层出 |
| **自研混合检索** | 索引粒度、过滤顺序、融合、阈值都要逐项调参并量化 | LlamaIndex 托管：把技术差异点藏进框架，讲不出调优过程 |
| **SQLite + FTS5 + jieba 预分词** | 3–5 场会议的规模够用；中文必须预分词（unicode61 不切中文） | 专用向量库：MVP 规模用不上，numpy 暴力余弦毫秒级 |
| **官方 checkpointer** | 直接上 `langgraph-checkpoint-sqlite`，跨进程恢复是刚需 | 自研 saver：要自己处理序列化与版本兼容，返工风险高 |
| **FastAPI + 无构建前端** | 原型已定型，复用原型的设计令牌与三栏布局 | Streamlit：表达不了既定界面与 SSE 进度；React：单人项目引入构建链路收益不足 |
| **LLM 只走 API（DeepSeek）** | 换能力上限与开发效率；密钥走 `.env` 不入库 | 本地部署：显存与效果都不划算；代价（数据外发、成本）用缓存 / 预算 / 提示写清 |

### 2.5 质量数据：能摆到桌面上的数字（2 分钟）

**感知层（M2，真实模型）**：窗口级说话人准确率 **93.75%**、宏平均召回 **92.86%**、
片段级准确率 **100%**；端到端 RTF **0.093**（RTX 4060）/ **0.484**（CPU）。

**编排与检索（M3，22 条标注）**：Recall@8 **1.000**、MRR **0.881**（BGE 编码器）、
域外拒答正确率 **1.000**（阈值 0.35 → 0.50 是扫参扫出来的）。

**协同（M4）**：挂起 / 恢复 / 降级三条路径各有用例；人工确认后模型 payload 不被改写；
全量 382 项测试通过。

**评测（M5，语料 5 场 / 63 片段：3 场产品样例 + 2 场真实录音）**：

| 指标 | 离线（规则/模板） | 真实模型（DeepSeek） |
| --- | ---: | ---: |
| 意图路由准确率 | 0.676 | **0.882** |
| 多轮上下文保持 | 0.500 | **1.000** |
| 检索 Recall@8 / MRR | 0.796 / 0.579 | 同离线（检索不调模型） |
| 跨会议（严格 / 宽松） | 0.300 / 0.700 | 同离线 |
| 要点覆盖率 | 0.365 | **0.827** |
| 域外拒答正确率 | 0.938 | **1.000** |
| 纪要待办 F1 / 负责人 / 关键结论 / 风险 | 占位 | **0.833 / 1.000 / 0.714 / 0.400** |
| 重排消融（MRR / 检索 P95） | 0.579 → **0.661** / 0.9 ms → 162 ms | — |
| 一次全量真实评测 token | — | 输入 76,832 / 输出 13,499 |

**摆数字的姿势**：每个数字都标了"口径 + 能不能信"。
例如离线运行的纪要指标明确写成"占位内容，不是质量结论"；
证据正确率 0.452 同时说明"规则判定器在模型自由表达上偏严，需要人工抽样校准"。

### 2.6 工程约束如何落地（1 分钟）

| 约束 | 落地方式 |
| --- | --- |
| 无 GPU / 无 Key 也能跑 | 感知层双后端（offline / local）、LLM 三态（off / cache_first / live）、编码器三档（BGE / API / 哈希） |

| 文档不漂移 | `tests/test_docs.py`：190 项检查（章节、术语、开关、计划提到的模块是否真存在） |

## 3. 高频追问与回答要点

**Q1：这和"把录音丢给大模型总结"有什么区别？**

三处本质区别：① 检索优先于长上下文（会议库会变大，先把范围收窄到相关片段再让模型归纳）；
② 拒答先于生成（证据不达标就不调模型）；③ 证据校验后置（生成完再核每条结论是否被引用片段支撑）。
这三条都是可测试的工程约束，不是提示词技巧。

**Q2：你的 Agent 到底"自主"在哪？**

自主体现在决策点：意图路由（处理音频 / 查内容 / 查发言人）、范围解析（不确定就反问）、
是否调用检索、证据是否足够、是否需要重试、是否把结论打回人工确认。
每个决策点都有确定性的判据或可断言的路由结果——**不追求"看起来自主"，追求"每个决策讲得清"**。

**Q3：为什么不用 `AgentExecutor`？**

它的 ReAct 循环把 prompt 拼接、重试、解析都藏在框架里，路由结果无法在测试里断言，
与"路由必须可单测"这条硬约束冲突。换成 LangGraph 后，图只回答"什么时候调用谁"，
节点是纯函数，两条路径都能脱离框架单测。

**Q4：大模型幻觉怎么办？**

三层：① 检索层双闸拒答，证据不足直接不调模型；② 生成时只允许引用本次检索到的片段 ID，
越界引用丢弃；③ 生成后独立校验每条结论的支撑性，引用全丢的条目降级为待确认。
评测里专门有"域外拒答正确率"和"证据正确率"两项指标盯着它。

**Q5：多轮对话怎么保证不串场？**

范围（scope）随会话保存，"我说的是哪场会"只问一次；追问时把范围标记写进助手消息，
下一轮直接继承；历史上下文是"最近 3 轮原文 + 更早轮次摘要"，避免上下文线性膨胀。
检查点按 `conversation_id` 存，跨请求可恢复。

**Q6：成本怎么控制？**

四层：相同请求命中缓存（`llm_cache`，命中计 0 token）；限制上下文预算；
长会议 map-reduce；低难度决策（路由）可用小模型或规则。评测运行有 `--dry-run` 预演与
`MA_EVAL_TOKEN_BUDGET` 硬上限。真实评测一次全量约 9 万 token。

**Q7：你踩过哪些坑？（这题最能加分，讲三个）**

* **记账对象不一致**：`CachedLLMClient` 的累加器与节点上下文不是同一个对象，
  导致 token / 费用恒为 0——回答正常但账目全错。修复后补了回归测试。
* **`--offline` 悄悄打了真实 API**：评测只按运行类型打标签、没有强制关模型，
  于是"离线基线"跑了真实接口（93 秒、5.6 万 token）。现在 `prepare_settings` 强制置 `off`，有用例守着。
* **检查点序列化白名单不全**：只登记了 minutes 图的模型，chat 图的 `Answer` / `Draft` / `ChatResult`
  被静默拦掉（写进去、读出来是 None），多轮因为历史另有 DB 兜底所以没暴露。
  现在白名单补全，并有"状态必须能读回来"的用例。

**Q8：评测里最让你意外的一条是什么？**

范围解析（`resolve_scope`）按关键词匹配标题：真实语料里"官网改版项目短会"与样例的"官网改版周会"
共享"官网改版"，于是问"官网改版周会定了什么"时范围被放大到两场。
这是评测跑起来才发现的编排层缺陷（离线路由范围准确率 0.794），
正确做法是"精确 / 最长标题优先"——**评测的价值不只是打分，而是把这类问题暴露出来**。

**Q9：如果给你更多时间，先做什么？**

按报告里的失败归因排序：① 范围解析改成精确/最长标题优先；② 跨会议"汇总/比较"型问题
加一层聚合节点（现在 11 条检索未命中里 6 条属于这类，还有 1 条被误拒）；
③ 证据正确率用 LLM 判定 + 人工抽样校准；④ 风险项的匹配口径按证据对齐（现在纯文本，0.400 偏保守）。

**Q10：这个项目里哪些是你自己写的？边界在哪？**

编排、检索、评测、协同、前端集成都是在这个仓库里从零写的；
感知层的转写与声纹复用我实习项目的成果，重构为可独立调用的工具层
（`app/perception/`，offline / local 双后端），仓库里保留了对照与评测报告。
框架只用 LangGraph + langchain-core 的零件，检索引擎没有用任何 RAG 框架。

## 4. 演示与验证的"防翻车"清单

| 风险 | 兜底 |
| --- | --- |
| 现场没有网络 | 全链路可离线：`MA_LLM_MODE=cache_first` + `scripts/warm_cache.py` 预热；再不济 `off` |

| 想现场看代码结构 | `docs/操作教程.md` 末尾有目录速查；`app/agent/graph.py` 是唯一 import 框架的地方 |

## 5. MVP 边界：做完了什么、明确不做什么

**已完成（M1–M5 全部落地）**：

| 阶段 | 交付 | 状态 |
| --- | --- | --- |
| M1 骨架 | FastAPI + 无构建前端 + Pydantic 契约 + SQLite + 样例数据 | 完成 |
| M2 感知 | faster-whisper 转写 + ECAPA 声纹 + 离线后端；窗口级准确率 93.75% | 完成 |
| M3 编排与检索 | LangGraph 状态图、意图路由、混合检索（BM25 + 向量 + RRF）、带引用问答、map-reduce 纪要 | 完成 |
| M4 协同 | checkpointer + `interrupt` 挂起恢复、待确认区、override + 审计、证据回跳与音频定位 | 完成 |
| M5 评测 | 12 项指标、70/34/29 条标注、消融矩阵、Langfuse、一键复现 | 完成 |

**明确不做（《产品设计文档》3.2 已排除）**：实时录音与流式处理、账号与多租户权限、
日历 / 飞书 / 钉钉集成、多人协作编辑、移动端适配、pyannote 完整说话人分离、语音模型微调。

**已知短板（写在报告里，不藏）**：真实语料只有 2 场（片段 63，低于 100 的目标）；
范围解析在标题共享关键词时过宽；跨会议汇总型问题缺聚合层；
证据正确率仍以规则判定为主；费用未计价（价目表无对应模型）。
