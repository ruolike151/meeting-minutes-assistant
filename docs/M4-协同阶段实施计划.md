## 执行说明

**Goal**：把「人在回路」从**接口齐备**推进到**流程真的会停、确认后真的会走完**——用
checkpointer + `interrupt` 让待确认区挂起与恢复成为编排层的能力，把人工确认结果沉淀为
不可被重算覆盖的 override，并让每条引用都能跳回原声秒数核对。

**Architecture**：在 M3 已有的两张"事实"之上加一层协同：`chat` 图补上持久化 checkpointer
（thread_id = conversation_id），新增 `minutes` 图承载「生成 → 校验 → 待确认闸门 → 收尾」，
闸门处用 `interrupt` 挂起、`Command(resume=...)` 恢复；人工动作一律写 `action_item_overrides`
与 `review_events`，模型生成的纪要多行只读。所有节点仍是 `(state, context)` 纯函数，
LangGraph 只出现在图装配与 saver 两个文件里。

**Tech Stack**：Python 3.12 · FastAPI · Pydantic · SQLite（WAL + FTS5）· LangGraph
（`StateGraph` + checkpointer + `interrupt` / `Command`）· 原生前端（无构建）· pytest

**Spec**：本文档即 M4 的 spec 与实施计划，承接《技术方案》17 节 M4 行与《产品设计文档》
5.1 节 ④「待确认区」、7 节 ③「答案必须可溯源」。M5 的标注集、完整指标、重排与 Langfuse
**不在本文范围**（第 15 节）。

**MVP 范围说明（2026-09-12 拍板）**：本次只实现本文档的任务 T0–T8 与第 10 节的必答决策，
不做被列为"可选加分项"的内容——低置信度片段改发言人、审计面板、
对话内同步等待确认一律不做（记录在第 10 节与第 15 节，留给后续版本）。

## Global Constraints

全程适用，每个任务的要求都隐含包含这一节。

1. **C3 不回退**：`pytest` 必须在无网络、无 GPU、无模型权重、无 API Key 的机器上全绿。
   挂起与恢复属于编排层，测试一律用 `FakeLLMClient` + 临时 SQLite，不依赖真实模型。
2. **SSE 事件契约向后兼容**：M3 的 `stage` / `citation` / `delta` / `done` / `error`
   事件名与载荷形状不变；M4 只**新增** `review` 事件，不修改既有字段
   （`tests/test_frontend_contract.py` 与端到端契约用例继续全绿）。
3. **C4 不回退**：每条结论必须绑定可解析的片段 ID；人工确认不修改模型给出的
   `confidence`，只把把关人从阈值换成人工。
4. **挂起不阻塞**：任何等待人工确认的处理都不得占用感知层 worker（单线程池）。
   任务挂起后线程必须正常结束，恢复发生在新的 HTTP 请求里。
5. **模型产物只读**：`minutes.payload` 一旦写入不被人工操作改写；所有人工动作落
   `action_item_overrides`（M3 已有）+ `review_events`（M4 新增），重算纪要不得覆盖人工结论。
6. **依赖精确锁定**：新依赖装完立刻写回 `requirements.txt`（`==`）并刷新
   `requirements.lock.txt`；框架升级单独提交（《技术方案》15 节）。
7. **测试先行**：每个任务先写失败测试再实现，任务收尾时全量 `pytest` 通过。
8. **本地验证命令**（沙箱/CI 里 pytest 默认临时目录可能不可写，用工作区内的目录）：

```powershell
.\meeting_assistant\Scripts\python.exe -m pytest -q --basetemp=.pytest_tmp
.\meeting_assistant\Scripts\python.exe tests\test_docs.py
```

9. **密钥不入库**：API Key 只从环境变量或 `.env`（`.gitignore` 已排除）读取，
   不写进代码、不写进文档、不进日志、不入库；测试与 CI 不得依赖真实 Key。

## 1. 目标与验收口径

《技术方案》17 节对 M4 的定义是：

> **M4 协同**：checkpointer + interrupt 支撑待确认区；证据回跳；人工修改落 override 表。

《产品设计文档》5.1 节 ④ 给出产品口径：

> 声纹置信度低、负责人不明确、无截止时间的条目录入此处，用户确认 / 修改 / 丢弃后
> 再合并进最终稿。

结合 M1–M3 的实际状态（第 2 节），M4 的验收口径具体化为 8 条：

1. **挂起是真的挂起**：新会议生成纪要后若存在待确认条目，`minutes` 图在
   `review_gate` 处 `interrupt`，状态落 checkpointer，后台 worker 线程正常结束，
   会议与任务进入 `awaiting_review`（不再自动等于"处理完成"）。
2. **恢复是真的恢复**：`POST /api/review/{id}/resolve` 写 override 后，若该会议已无待确认
   条目，则由同一个 thread 恢复图并跑到 `finalize`，会议转 `processed`；重复确认幂等。
3. **降级可用**：checkpoint 文件被删除或 `MA_REVIEW_MODE=off` 时，确认接口仍能直接依据
   数据库收尾（不 500、不丢数据），这是"别人克隆仓库也能跑通"的底线。
4. **待确认区覆盖完整**：待办（负责人不明确 / 无截止时间 / 低置信度）与低置信度决议都进
   待确认区，前端能区分条目类型并分别给出可用的处理动作。
5. **override 不可被覆盖**：重新生成纪要后，已确认 / 已丢弃 / 已改派的结果保持不变
   （回归用例断言）。
6. **证据回跳**：回答中的引用 chip 点击后，无论引用属于当前会议还是别的会议，都能打开
   对应会议的原声视图并高亮该片段；会议有音频时播放器定位到该片段起点。
7. **状态机一致**：会议列表与会议详情返回的 `status` / `review_count` 与待确认区一致，
   不存在"徽标显示 2 条但点进去为空"。
8. **零回归**：M1–M3 的全部用例继续通过；`web/` 不引入任何构建链路与新前端依赖。

**建议验收阈值**

| 验收项 | 口径 | 目标值 |
| --- | --- | --- |
| 自动化测试 | `pytest`（无网络 / 无模型 / 无 Key） | 全绿；用例数 290 → **≥ 320** |
| 挂起 | 2 条待确认条目的会议 | `interrupt` 触发 1 次；任务 `awaiting_review`；worker 线程 0 阻塞 |
| 恢复 | 逐条确认到清空 | 会议转 `processed`；重复确认返回 200 且不重复写审计 |
| 降级 | 删除 checkpoint 库后再确认 | 会议仍能转 `processed`；接口无 5xx |
| 待确认覆盖 | 待办 + 决议 | 低置信度决议进待确认区；确认后不再出现在列表 |
| override | 重新生成纪要后读取 | 人工结论保持（用例断言） |
| 证据回跳 | 单会议、跨会议、无音频三种场景 | 均能定位高亮；有音频时误差 ≤ 0.5s |
| 事件契约 | SSE 事件名与载荷 | 既有事件逐字段一致；`review` 为新增事件 |

阈值是建议起点：真实数字以 T8 的端到端与验收报告为准，行为改动必须附前后对比。

## 4. 架构与文件结构

### 4.1 两张图，各管一段

```text
chat 图（已有，M4 补 checkpointer）
  START → route → … → finalize → END         thread_id = conversation_id
  作用：会话状态（scope / history）跨请求可恢复

minutes 图（M4 新增，唯一新增的编排结构）
  START → generate → validate
            ├─(schema 非法 且 retry < 2)→ generate
            └─(合法)→ review_gate
                        ├─(有待确认条目)→ interrupt(挂起载荷)→ END(线程结束)
                        └─(无)→ finalize → END
  thread_id = meeting_id
  作用：把"生成纪要"到"可以交付"之间的人工确认显式建模成图的一步
  恢复：POST /api/review/{id}/resolve → Command(resume=…) → review_gate 重入 → finalize
```

为什么闸门放在 `review_gate` 而不是 `generate` 里：`interrupt` 恢复时会**重新执行包含它的
节点**。闸门节点只读状态、不调模型；昂贵的生成节点在它上游，结果已经落在 checkpoint 里，
因此恢复不会重复花钱。

### 4.2 挂起与恢复时序

```text
上传音频 ──► run_task（worker 线程）
              感知层 → segments 入库
              minutes 图 invoke(thread_id=meeting_id)
                generate（LLM，map-reduce）→ validate
                review_gate 发现 2 条 needs_review
                  → interrupt(payload) → 检查点落盘 → invoke 返回
              tasks.status=done, meetings.status=awaiting_review
            （worker 线程结束，不等待人工）

用户确认第 1 条 ──► POST /api/review/{item}/resolve
              写 action_item_overrides + review_events
              仍有 1 条待确认 → 不恢复图，返回"还剩 1 条"

用户确认第 2 条 ──► 写 override + 审计
              待确认为空 → minutes_graph.invoke(Command(resume=…), thread_id)
                review_gate 重入 → finalize → meetings.status=processed
              返回"纪要已完成"
```

## 5. 关键设计

### 5.1 挂起载体：持久化 checkpointer + interrupt

推荐方案（决策 ① 的 A）：引入 `langgraph-checkpoint-sqlite` 的 `SqliteSaver`，检查点库
放在 `<data_dir>/checkpoints.sqlite`，与业务库分开。

* **为什么分文件**：检查点表是框架 schema（版本随 LangGraph 走），业务表是我们自己的
  schema（`PRAGMA user_version` 管）；分开后清空会话状态不影响会议数据，升级框架也不会
  搅动业务迁移。
* **为什么不用 `InMemorySaver`**：挂起发生在后台 worker 线程，恢复发生在后续 HTTP 请求，
  两个线程、两次调用之间没有共享内存；不落盘的 saver 一挂起就丢状态。
* **thread_id 口径**：`chat` 图用 `conversation_id`，`minutes` 图用 `meeting_id`。
  两者都已经是稳定主键，不需要新增 ID 生成规则。
* **saver 的三态**：`MA_CHECKPOINT_BACKEND=sqlite`（默认）/ `memory`（测试用）/
  `off`（不挂起，直接顺序执行 + 收尾），与 C3 的"每个外部依赖都有兜底"一致。
* **纪律**：`import langgraph.checkpoint` 只允许出现在 `app/agent/checkpoint.py`，
  `StateGraph` 只允许出现在 `app/agent/graph.py`，用静态断言测试守住（T0 落地）。

### 5.2 闸门的输入：这次有哪些条目需要人工确认

```python
def pending_items(conn, meeting_id: str) -> list[ReviewItem]:
    """待确认条目 = 合并 override 之后仍然 needs_review 的条目。"""
```

要点三条：

1. **判据只看合并后的结果**，不看模型原始输出——人工已经确认过的条目不该再次挂起；
2. **判据必须可从数据库重建**（`minutes` + `action_item_overrides`），不能只存在状态里，
   否则 checkpoint 丢失就再也算不出"还剩几条"；
3. **覆盖范围**（待办 / 决议 / 片段归属）见决策 ②，默认实现为待办 + 决议。

### 5.3 override 是唯一事实源

沿用 M3 的三态语义，M4 只补两点：

* **新增 `edit` 动作**：改派负责人 / 改截止时间时不改变 `resolution`（仍为 pending 或
  confirmed），只写 `owner` / `due`；前端"确认并改派"等价于一次 `edit` + 一次 `confirm`。
* **新增审计**：每次人工动作写 `review_events(meeting_id, item_id, action, before, after,
  actor, created_at)`。它不是冗余——M5 的"人工介入率 / 驳回率"指标直接取自这张表，
  面试时也是"人在回路可度量"的证据。

模型产出的 `minutes.payload` 保持只读：重新生成纪要 = 覆盖 payload，人工结论 = 覆盖
override，两者在读取时合并（`MinutesRepo.get_with_overrides`）。

### 5.4 恢复的降级路径

恢复函数按顺序尝试，任何一步失败都不影响数据正确性：

```text
确认 / 丢弃 / 改派
  → 写 override（业务事实，必须成功）
  → 写 review_events（审计，失败只记日志）
  → 若仍有待确认条目：直接返回"还剩 N 条"
  → 若无待确认条目：
      有 checkpoint → invoke(Command(resume=…), thread_id) 跑到 finalize
      无 checkpoint 或 backend=off → 直接 finalize（写状态 + 审计）
```

这条降级同样覆盖"用户删了 data 目录又不想重跑会议"的场景，并且让
`MA_REVIEW_MODE=off` 成为可评测的消融开关（M5 用来量化"人在回路带来的质量增益"）。

### 5.5 会议与任务状态机

```text
meetings.status:  processing → awaiting_review → processed
                        └────────────(无待确认条目)────────┘
                        └────────────(生成失败)───────────► failed
tasks.status:     queued → running → done（notes 记录是否待确认）/ failed
                 tasks.stages 末尾追加 "等待人工确认" 阶段，进度条停在 90% 而不是 100%
```

`review_count` 由 `pending_items` 计算，会议列表与详情共用同一个函数，避免两处口径
漂移（验收项 7）。

### 5.6 证据回跳：从引用 chip 到原声秒数

| 场景 | 现状 | M4 |
| --- | --- | --- |
| 引用属于当前会议 | ✅ 切原声 tab + 高亮 + 滚动 | 保持 |
| 引用属于别的会议 | ❌ `openSegment` 在 `meetingById` 查不到时静默返回 | 按 `data-mid` 拉详情、必要时同时加载会议列表，再定位 |
| 会议有音频 | ❌ 无端点、无播放器 | `GET /api/meetings/{id}/audio`（FileResponse，支持 Range）+ 播放器定位 `segment.start` |
| 会议无音频（样例数据） | — | 播放器隐藏，只高亮，不报错 |
| 片段不在当前 DOM（未渲染的分页） | — | 先切原声 tab 再查找元素，找不到时降级为"打开会议详情 + toast 提示" |

### 5.7 前端改造范围（无构建、无新依赖）

* 待确认区分两组渲染：**待办**（负责人 / 截止时间 / 证据）与**决议**（内容 / 置信度 / 证据）；
* 每条支持三个动作：确认通过、修改后确认、忽略；编辑态用内联表单，不引入组件库；
* `store.dismissed` 保留为乐观状态，但请求失败必须回滚并提示（现状是"先乐观、失败不管"）；
* 音频播放器用原生 `<audio>` + 现有的设计令牌样式；
* 所有新增字段走 `tests/test_frontend_contract.py` 的静态检查，防止前端读不存在的字段。

```sql

CREATE TABLE IF NOT EXISTS review_events(
    id         TEXT PRIMARY KEY,

    item_id    TEXT NOT NULL,

);

CREATE INDEX IF NOT EXISTS idx_review_events_meeting ON review_events(meeting_id, created_at);
```

  `MIGRATIONS`（它不是业务 schema），但要在 `bootstrap` 里初始化一次；

## 12. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| `interrupt` 恢复时重复执行上游昂贵节点 | 重复调用 LLM、费用翻倍 | 闸门节点不调模型；生成结果先进 checkpoint；用 `llm.calls` 计数断言恢复过程零额外调用 |
| 检查点库与业务库数据不一致 | 会议卡在 `awaiting_review` 无法收尾 | 恢复判据只用业务库（`pending_items`）；checkpoint 只做"能否复用图"的优化，降级分支兜底（5.4） |
| 挂起后用户永不处理 | 会议永远是"处理中"，看板脏 | 任务 stages 停在"等待人工确认"；会议列表按 `status` 过滤；提供"全部忽略并收尾"的批量动作（T5 落地） |
| SQLite 并发写（worker + 请求 + 检查点） | `database is locked` | 沿用 WAL；检查点独立文件降低竞争；写操作短事务，失败重试一次并记日志 |
| 决议进入待确认区导致条目暴涨 | 用户疲劳，演示效果差 | `MA_REVIEW_MAX_ITEMS` 上限 + 阈值可调；M5 用"人工介入率"指标评估阈值是否合理 |
| 音频端点目录穿越 | 读到 `data/` 之外的文件 | 路径必须 `resolve()` 后位于 `audio_dir` 内，用例覆盖 `../` 与绝对路径 |
| 前端新增交互破坏既有契约 | 页面空白 | `test_frontend_contract.py` 静态检查 + 端到端用例作为门禁 |
| 范围膨胀（顺手把 M5 的事做了） | M4 交付延期 | 第 15 节划界；重排、Langfuse、标注集一律归 M5 |
