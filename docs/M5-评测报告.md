### 真实语料怎么进来的

`samples/annotations/meeting.demo.json` / `meeting2.demo.json` 是上游的转写标注，
`scripts/build_eval_corpus.py` 把它们 + 人工纪要金标（`real_minutes_gold.json`）
合成 `real_meetings.json`（2 场 / 31 片段），评测运行器再把语料灌进**评测专用**数据目录。

这样做的两个理由：正文机械转换可重复、来源可追溯；产品样例库不受评测语料变动影响。

`GROUP`（B/C/D 合说）在领域模型里没有承载字段，按 `speaker_id=null` + 置信度 0.5 处理
（与 M2 感知层的口径一致），检索与纪要评测照常使用其文本。

## 4. 消融矩阵

| 配置 | 编码器 | Recall@8 | MRR | 跨会议(严/宽) | 域外拒答 | 域内作答 | 路由准确率 | 证据正确率 | 要点覆盖 | 待办 F1 | 检索 P95 | 总耗时 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| RRF-only（M3 默认） | hash#256 | 0.796 | 0.579 | 0.300 / 0.700 | 0.938 | 0.926 | 0.676 | 0.355 | 0.365 | 1.000* | **0.9 ms** | 15.4 s |
| + cross-encoder 重排 | hash#256 | **0.833** | **0.661** | 0.300 / 0.700 | 0.938 | 0.926 | 0.676 | 0.376 | 0.423 | 1.000* | **162 ms** | 109.3 s |

\* 离线运行的待办 F1 是"占位内容 vs 金标"的接线验证，不是质量数字（见第 7.3 节真实值）。

### 重排结论（关闭 M3 决策 ③）

1. **MRR 0.579 → 0.661（+14.1%）**，Recall@8 从 0.796 升到 0.833，
   证据正确率与要点覆盖率同步上升（0.355→0.376、0.365→0.423）。
2. **代价**：单查询检索 P95 从 0.9 ms 涨到 162 ms（CPU，`bge-reranker-base`，top-20 候选），
   整轮评测从 15 s 涨到 109 s。
3. **按预注册门槛判定**（MRR +3%、延迟 +≤300 ms）：**两项都满足 → 重排是有效的质量升级**。
4. **默认值保持 `off`**：零权重、零额外依赖是 C3 基线；重排作为实测有效的可选项
   （`MA_RERANK_MODE=cross_encoder`）。真实语料下收益比原先（+13.6%）还略高，
   说明"排序质量影响答案质量"不是小样本巧合。

## 5. 失败明细与归因

### 5.1 检索：11 / 50 未命中

| 未命中查询 | 原因 |
| --- | --- |
| 前端开发现在卡在哪一步 | 改述与原文（"在等设计稿定稿"）几乎无字面重合，hash 编码器救不回来 |
| 开发拿不到设计稿会怎么样 | 同上（跨句推理） |
| 点击转化率比预期低的原因是什么 | 真实录音里的表述是"转化率比预估略低""物料不足"——需要语义改写能力 |
| 接下来三天各岗位分别负责什么 | 需要把三段分工合并成一份答案（多跳） |
| 明天下午还有什么安排 | 原文是"明天下午我们再做一次简短进度抽查"，关键词命中不足 |
| 三场会里分别有哪些待办 / 谁在会议上被分配了任务 / 各场会的下一步动作分别是什么 / 有没有跨会议都出现的问题 | 跨会议"汇总 / 比较"型问题，单轮检索做不到 |
| 两场会议里设计侧都提到了哪些事 / 两次会议最后都是怎么收尾的 | 同上（跨会议多跳） |

**结论**：11 条里 6 条是"汇总 / 比较"型问题、3 条是强改述。前者属于编排层的聚合能力
（先按会议分组检索、再聚合、再合成），后者需要语义编码器而不是哈希兜底。
两条下一步都很明确：报告只负责把它们量化出来。

### 5.2 证据正确率 0.355 的归因

离线运行的回答是模板装配（模型关闭）：结论句由检索片段拼出来，
"结论 ↔ 片段"的关键词覆盖率天然偏低。这不是引用错了（引用越界率 7.5% 指向的是
范围解析问题，见第 5.4 节）。真实模型下同一指标为 **0.452**（第 7.2 节），
说明提高该指标的关键是"让模型基于证据写结论"，而不是调规则阈值。

### 5.3 跨会议：严格 0.300 / 宽松 0.700

严格口径要求返回片段**全部**落在允许的会议集合内；10 条里 3 条满足。
失败的都是第 5.1 节的汇总型问题（返回空或命中第三场会议的相关片段）。
宽松口径（捞到过对的会议）为 0.700。两个数字一起看才有意义：
**问题是"跨会议聚合能力不足"，不是"检索引擎找不到"**。

### 5.4 路由：11 / 34 未过（离线规则模式）

| 未过查询 | 期望 → 实际 | 原因 |
| --- | --- | --- |
| 官网改版周会定了什么？ / 官网改版的风险点是什么 / 官网改版周会要做什么 | 范围都多了 `m_real_1` | **标题共享关键词时范围过宽**：真实语料里的"官网改版项目短会"与样例的"官网改版周会"都含"官网改版" |
| 官网改版项目短会有什么风险 | 范围多了 `m_20260911` | 同上（对称的一侧） |
| 新品推广活动复盘会和官网改版项目短会分别有哪些待办 | 范围多了 `m_20260911` | 同上 |
| 谁提到了活动弹窗的问题？ | 范围收窄到 `m_real_2`，期望全库 | 话题词误命中会议标题 |
| E 这周要做什么 / 那C 要做什么 | speaker_tasks → speaker_speech | 规则句式覆盖不足 |
| 帮我总结一下这几场会议 | clarify → content | 泛指总结的澄清触发词没覆盖这种说法 |
| 移动端体验专项讨论最后定了哪些事 | decisions → content | 规则里的"定了什么"没覆盖"最后定了哪些事" |

**这是本次评测最有价值的发现**：范围解析（`app/agent/routing.py::resolve_scope`）
按关键词匹配标题，两场会议标题共享"官网改版"时会把范围放大到两场。
正确做法是**精确 / 最长标题优先**（或提高 token 覆盖率门槛），
属于编排层的小改动——留作下一步，M5 只把它测出来。
真实模型路由把这一项从 0.676 提到 **0.882**（第 7.1 节），说明模型能弥补一部分规则缺陷。

### 5.5 拒答：1 条域外漏放、1 条域内误拒

* "世界杯什么时候开始"被放行：覆盖率与余弦都没有同时低于阈值（15/16）；
  下一步在新标注集上重扫阈值（`scripts/eval_retrieval.py --sweep`），并把域外样本扩到 30 条。
* "这几场会一共定了哪些事？"被误拒：跨会议汇总型问题被检索闸门拦下，与第 5.1 节同源。

## 7. 真实模型运行（DeepSeek）

### 7.1 对话行为：路由 0.676 → 0.882，多轮 0.500 → 1.000

| 指标 | 离线（规则） | 真实（模型优先） |
| --- | ---: | ---: |
| 意图路由准确率 | 0.676 | **0.882** |
| 意图 / 模式 / 范围 | 1.000 / 0.882 / 0.794 | 1.000 / 0.941 / 0.941 |
| 多轮上下文保持 | 0.500 | **1.000** |

模型补上了规则没覆盖的句式（"最后定了哪些事""要做什么""总结一下这几场会议"），
但范围解析仍受"标题共享关键词"影响（0.941 而非 1.000）。

### 7.2 问答质量

| 指标 | 离线（模板） | 真实（LLM 合成） |
| --- | ---: | ---: |
| 证据正确率（规则版） | 0.355 | **0.452** |
| 要点覆盖率 | 0.365 | **0.827** |
| 引用越界率（会议粒度） | 0.075 | 0.107 |
| 域外拒答正确率 | 0.938 | **1.000** |

**要点覆盖率 0.365 → 0.827** 是最能说明问题的一组数字：模型合成把"检索到的片段"
变成了"回答到点上"。同时证据正确率只有 0.452——规则判定器在**模型自由表达**上偏严
（结论句是模型写的，关键词不一定与片段重合），这正是需要 `MA_JUDGE_MODE=llm`
与人工抽样校准的地方（下一步）。

### 7.3 纪要质量（5 场会议，一次完整运行）

| 指标 | 实测 | 说明 |
| --- | ---: | --- |
| Schema 合法率 | **1.000** | 含校验重试与单条降级 |
| 待办抽取准确率 / 召回率 / F1 | 0.750 / 0.938 / **0.833** | 按"文本相似或证据片段重叠"匹配 |
| 负责人归属准确率 | **1.000** | 抓到的人一个没错 |
| 关键结论命中率 | **0.714** | 10 / 14，按证据片段对齐 |
| 风险命中率 | 0.400 | 2 / 5，仍是纯文本匹配（见下） |

逐场（待办 预测 / 金标 / 匹配）：`m_20260911` 5/4/4、`m_20260909` 2/2/2、
`m_20260904` 2/3/2、`m_real_1` 3/3/3、`m_real_2` 8/4/4。
漏抽的两条是"新增积分流水表并实现滚动 12 个月等级计算""负责老机型兼容测试"，
多抽的是模型把一条待办拆成了几条（`m_real_2` 8 条 vs 金标 4 条）。

**匹配口径本身也修过一次**：最初只按事项文字相似度（difflib ≥0.75）匹配，
真实模型把"交付设计稿"写成"完成配色微调并交付全套设计稿"就判成没命中，
F1 只有 0.105。改成"文本相似**或**证据片段重叠（≥0.5）"后为 0.833——
这条口径与本项目"每条结论绑定片段 ID"（C4）一致，也更能反映真实质量。
**风险**还是纯文本匹配，所以 0.400 同样偏保守，下一步按同一口径改造。

### 7.4 可观测（Langfuse 自托管）

本机 Docker 起来了自托管 Langfuse（`docker-compose.langfuse.yml`：
web + worker + postgres + clickhouse + redis + minio 六个容器，
用 `LANGFUSE_INIT_*` 做 headless 初始化，免注册），并验证了链路：

```text
两轮对话 → chat_traces（本地，事实源）+ LangfuseTraceSink
        → Langfuse API 查询：同一会话聚合成 1 条 trace，含 4 个 observation
```

验证要点：`conversation_id`（`c_xxx`）不是合法 trace id，直接上报会被忽略，
因此 `to_trace_id()` 做了一次确定性哈希（`c_xxx` → 32 位 hex），
**同一会话永远映射到同一条 trace**；上报失败只记 warning，不影响回答。
未启用（默认）时 `build_sink()` 返回空实现且**不 import langfuse**（有用例守住）。

## 8. 局限与下一步

1. **语料规模**：5 场 / 63 片段已达"会议数"目标，但片段数仍低于 100——
   两场真实录音本身只有 31 段，属素材上限，不再新增录音（用户已确认）。
2. **纪要真实质量刚刚建立基线**：F1 0.833 / 结论 0.714 / 风险 0.400，
   其中风险项仍是纯文本匹配，下一步按证据口径改造。
