## 2. 三档编码器的对比（min_cosine=0.50，k=8）

| 编码器 | Recall@8 | MRR | 拒答正确率 | 作答率 | 建索引耗时 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `keyword-only`（M1 基线，无向量） | 1.000 | 0.857 | 1.000 | 1.000 | 0.5 s |
| `hash-bigram-v1#256`（零依赖兜底） | 1.000 | 0.809 | 1.000 | 1.000 | < 0.1 s |
| `bge-small-zh-v1.5#512`（本地语义） | 1.000 | **0.881** | 1.000 | 1.000 | 9.3 s（CPU，含加载权重） |

**如实解读，不粉饰：**

1. **召回在这份标注集上已经饱和**（三档都是 1.000）：例子只有 14 条，
   而且问题里的措辞大多与转写原文重合，关键词检索就能覆盖。
   要看出语义检索的差距，需要更大的标注集（M5 的任务）；
2. **向量路的价值体现在排序上**：BGE 把 MRR 从 0.857 抬到 0.881（+2.8%）。
   幅度不大，但方向正确，且不需要人工维护同义词表；
3. **哈希兜底不提升排序质量**（MRR 0.809，比关键词基线低）：
   它只捕捉字面重合，混进 RRF 反而稀释了 BM25 的排名。
   所以它的定位是"无权重机器上让链路可跑、可测"，**不是**效果方案；
4. 三档的拒答正确率都是 1.000，说明拒答机制不依赖某一种编码器——
   这是"不编造"这条产品原则的工程底线。

## 3. 阈值取舍：min_cosine 0.35 → 0.50

初始值 0.35 来自《技术方案》9.1，实测**偏松**：中文 BGE 会把"公司食堂今天中午吃什么"
这类域外问题映射到 0.4~0.6 的相似度区间，于是一半以上的域外问题被放行。

| min_cosine | Recall@8 | MRR | 拒答正确率 | 作答率 |
| ---: | ---: | ---: | ---: | ---: |
| 0.35（原始默认） | 1.000 | 0.881 | **0.250** | 1.000 |
| 0.45 | 1.000 | 0.881 | 0.625 | 1.000 |
| **0.50（新默认）** | 1.000 | 0.881 | **1.000** | 1.000 |
| 0.55 | 1.000 | 0.881 | 1.000 | 1.000 |

取 0.50 而不是 0.55：两个值在当前标注集上表现相同，取更低的那个能给域内问题留更多余量
（阈值越高，越容易把"说法比较绕"的真实问题一起拒掉）。这个结论的置信度受标注集规模限制，
M5 扩标注集后要重扫一次。

复现：

```powershell
.\meeting_assistant\Scripts\python.exe scripts\eval_retrieval.py --encoder bge --sweep
```

**结论**：参数是扫出来的，不是拍出来的；改阈值必须附前后对比（《技术方案》9.3）。

## 5. 真实 LLM 实测（2026-09-12）

配置：`MA_LLM_BASE_URL=https://api.deepseek.com`、模型 `deepseek-flash`、`MA_LLM_MODE=live`、
本地 BGE 向量、全新数据目录（无缓存）。

复现：

```powershell
$env:MA_RUN_LLM_SMOKE = "1"
.\meeting_assistant\Scripts\python.exe scripts\eval_llm_smoke.py
```

### 5.1 单次问答

| 问题 | 回答形态 | 引用 | input | output | 实际调用次数 |
| --- | --- | ---: | ---: | ---: | ---: |
| 谁提到了活动弹窗的问题？ | attribution | 1 | 2247 | 227 | 2（路由 + 合成） |
| 退款之后积分怎么处理？ | content | 5 | 1911 | 435 | 2 |
| 首屏为什么慢？ | content | 2 | 2133 | 588 | 2 |
| 公司食堂今天中午吃什么？ | refuse | 0 | 872 | 95 | **1（只有路由）** |
| **合计** | | | **7163** | **1345** | 7 |

最后一行是"拒答先于生成"的直接证据：域外问题只花了路由那一次调用，
**合成这一步根本没有执行**——省下的不只是钱，还有"模型自由发挥"的机会。

### 5.2 单场会议的纪要生成

对象是 M2 用 faster-whisper small + ECAPA 处理过的那场真实录音（86.5 秒、4 人、7 条转写片段）：

```powershell
curl -X POST http://127.0.0.1:8000/api/meetings/m_smoke/minutes/regenerate
```

| 项 | 实测 |
| --- | --- |
| LLM 调用次数 | 1（片段未超预算，单段直通，未触发 reduce） |
| input / output token | 1720 / 1079 |
| 产出 | 4 个主题、4 条决议、3 条待办、0 未决、0 风险 |
| 待确认区 | 3 条待办中 **2 条**因缺截止时间自动进入待确认区 |
| 负责人归属 | 3 条待办全部映射到声纹库身份（`owner_source=explicit`） |

也就是说，"上传音频 → 转写 → 声纹 → LLM 纪要 → 待确认区"这条路已经是真数据跑通的，
不是样例数据的演示。

### 5.3 费用

价目表里没有 `deepseek-flash`，因此落库的费用记 0——这是有意的：
不拿另一个模型的单价硬套出一个看起来精确的错数字。token 数字来自 API 返回，是准确的。

想看到金额，在 `.env` 里设置 `MA_LLM_PRICE_INPUT` / `MA_LLM_PRICE_OUTPUT`（元 / 百万 token）。
若按 DeepSeek 公开的 deepseek-chat 参考价（输入 1 元、输出 2 元每百万 token）粗估：

| 场景 | 粗估费用 |
| --- | ---: |
| 四问合计（7163 in / 1345 out） | ≈ 0.0099 元 |
| 单场 86.5 秒会议纪要（1720 in / 1079 out） | ≈ 0.0039 元 |

即"处理一场会 + 问几个问题"都在**一分钱量级**，成本口径站得住。

### 5.4 实测中发现并修掉的一个真 bug

第一次跑冒烟时，回答正常但 `chat_traces` 里 token 与费用全是 0。查库发现
`llm_cache` 有 7 条真实记录（说明调用确实发生了），问题出在记账：
`CachedLLMClient` 把用量记在自己的累加器里，而节点上下文另起了一个，
两边不是同一个对象。修复后由 `build_context` 直接复用客户端的累加器，
并加了回归测试 `tests/test_graph.py::test_llm_usage_reaches_chat_trace`。

这条留在报告里的意义是：**"有没有真的记账"必须靠一次真实调用才能验出来**，
假实现跑一万遍也只会显示 0。
