版本：v0.3　　日期：2026-09-11　　状态：待评审
配套文档：《技术方案》（`docs/技术方案.md`）
更改记录：v0.3 定稿技术选型（前端 FastAPI + 轻前端、编排 LangGraph、检索层自研）；
v0.2 收敛 MVP 范围。

---

## 1. 项目定位

一个**对话式会议助手**：把会议录音变成可检索、可追溯、可追问的会议知识库。

用户不需要学习任何操作流程，直接提问即可：

- 「帮我把这几个录音整理成纪要」→ 处理音频，产出纪要
- 「上周项目周会定了什么」→ 检索历史会议并回答
- 「张工这周一共答应了哪些事」→ 按发言人维度汇总

**一句话**：输入可以是音频，也可以是问题；输出的答案永远带原文证据。

**项目属性**：面向 Agent 开发岗位的能力展示项目。主体是对话式 Agent 的
意图路由、工具编排、检索策略与上下文管理；语音转写和声纹识别作为可替换的
工具层存在。

因此技术选型本身也是展示内容：编排必须显式、可控、可测试，每个选型都要讲得出
「为什么是它、为什么不是另一个」（见《技术方案》第 4 节）。

---

## 2. 目标用户与使用场景

**目标用户**：需要整理和回溯会议内容的团队负责人、项目成员。

**三类典型场景**：

| 场景 | 用户输入 | 系统产出 |
| --- | --- | --- |
| 会后即时整理 | 上传会议音频 | 结构化纪要 + 待办清单 |
| 历史信息回查 | 「上次评审会关于登录改版是怎么定的」 | 带原文引用的回答 |
| 发言人维度追踪 | 「李工承诺了哪些事」「这个问题是谁提的」 | 按人汇总的发言与待办 |

**用户核心诉求**：

1. 不想重听录音 —— 要能快速读完要点；
2. 想知道"谁答应了什么事、什么时候交" —— 待办要能落到人；
3. 不敢直接相信 AI 的结论 —— 每条结论都能一键回到原话核对；
4. 能连续追问 —— 不用每次重述"我说的是哪场会"。

第 3 点与第 4 点决定了本产品区别于普通"AI 摘要工具"的形态。

## 3. MVP 范围

### 3.1 本期要做

| 模块 | 内容 |
| --- | --- |
| 对话式入口 | 单一对话框，同时支持自然语言提问与音频上传 |
| 意图路由 | 自动区分"处理新音频"与"查询已有会议"，并判断查询范围 |
| 会议处理 | 转写 + 说话人识别 + 生成结构化纪要 |
| 会议库 | 所有已处理会议持久化，可列表、可检索、可进入详情 |
| 检索问答 | 跨会议 / 单会议 的片段级检索，带引用的回答 |
| 发言人查询 | 按人汇总发言内容、承诺事项、出现场次与发言时长 |
| 证据链 | 答案绑定片段 ID 与时间戳，支持回跳核对 |
| 人机协同 | 低置信度条目录入「待确认区」，人工确认后才进最终稿 |
| 导出 | 纪要 Markdown、待办 CSV、结构化 JSON、对话记录 |
| 评测 | 固定测试集，量化纪要质量、检索效果与对话行为 |

### 3.2 本期不做（明确排除）

实时录音与流式处理、账号体系与多租户权限、日历 / 飞书 / 钉钉集成、多人协作
编辑、移动端适配、pyannote 完整说话人分离、语音模型微调。

MVP 的验收标准是**能在 15 分钟内讲清一条完整闭环**，范围一大就讲不清。

## 4. 整体流程

对话是唯一主入口，音频上传是对话中的一种动作。

```text
用户在对话框输入（文字提问 / 上传音频）
        │
        ▼
① 对话 Agent：意图路由
        │
        ├── 路径 A：处理新音频
        │     感知层：音频标准化 → 转写 → 声纹匹配 → 身份对齐
        │     → 结构化片段 → 入库
        │     → 生成纪要（长会议分段 map-reduce）→ schema 校验
        │     → 返回纪要卡片
        │
        ├── 路径 B：查询会议内容
        │     检索层：锁定会议范围 → 片段检索（关键词 + 语义）
        │     → 组装证据上下文 → LLM 归纳 → 带引用的回答
        │
        └── 路径 C：查询发言人
              发言人索引 → 汇总发言 / 承诺事项 / 出现场次
              → 带引用的回答
        │
        ▼
② Web 展示：对话流 + 证据卡片 + 会议库侧栏
        │
        ▼
③ 人工确认：低置信度条目在待确认区处理
        │
        ▼
④ 导出与会话留存
```

## 5. 功能模块

### 5.1 Web 页面层

以对话为主区，会议库为侧栏。

**实现载体**：FastAPI 提供 HTTP 服务与静态资源，前端为无构建的轻量页面
（原生 HTML / CSS / JS，沿用 `prototype/` 的三栏布局与设计令牌），不引入前端
框架与打包链路。页面用 REST 发起操作，用 SSE 接收长任务进度。

**① 对话区（主区）**

- 消息流形式的自然语言交互，支持连续追问；
- 输入框同时支持文字与音频文件（拖拽或选择上传）；
- 回答中内嵌证据引用标记，点击展开对应原文片段与时间戳；
- 长任务（音频处理）显示阶段进度，不阻塞对话。

**② 会议库侧栏**

- 已处理会议列表：标题、日期、时长、参会人、处理状态；
- 支持按标题 / 日期 / 参会人筛选；
- 点击进入单场会议详情，并可发起针对该场会议的追问。

**③ 纪要视图**

单场会议的结构化纪要：摘要（分主题）、决议、待办（负责人 / 事项 / 截止时间 /
状态 / 证据）、待确认问题、风险。

**④ 待确认区**

声纹置信度低、负责人不明确、无截止时间的条目录入此处，用户确认 / 修改 / 丢弃后
再合并进最终稿。

### 5.2 对话 Agent 层（核心）

这是与"一个大 prompt 直接出摘要"的本质区别，也是面试讲解的重点。

| 能力 | 说明 |
| --- | --- |
| 意图路由 | 判断本次输入是「处理新音频」还是「查询」，并确定查询范围 |
| 工具调用 | Agent 主动调用工具获取信息，而非被动接收全文 |
| 澄清追问 | 信息不足时反问用户（"你指的是哪场会议？"），不做猜测 |
| 多轮上下文 | 维护会话状态；长结果压缩后进入上下文，避免无限增长 |
| 检索优先 | 先缩小范围再读取内容，而非把整个会议库塞进上下文 |
| 结构化生成 | 纪要按 schema 生成，校验失败自动携带错误重试修复 |
| 拒答机制 | 检索不到证据时明确说明"未找到"，不编造 |
| 成本与可观测 | 记录工具调用链、耗时、token 与单次成本 |

**工具集**：

| 工具 | 职责 |
| --- | --- |
| `process_audio` | 新建会议处理任务（转写 + 声纹 + 生成纪要） |
| `list_meetings` | 列出 / 筛选已有会议 |
| `get_minutes` | 取单场会议的结构化纪要 |
| `search_segments` | 片段级检索，支持按会议、发言人、时间范围过滤 |
| `query_speaker` | 发言人维度汇总（发言、待办、场次） |
| `update_action_item` | 修改待办状态 / 负责人 / 截止时间 |
| `flag_uncertainty` | 将存疑条目录入待确认区 |

### 5.3 感知层（工具层）

复用历史项目的音频处理与转写成果，重构为可独立调用的工具，而非单体脚本。

| 工具 | 职责 | 输入 → 输出 |
| --- | --- | --- |
| `transcribe_audio` | 语音转写 | 音频路径 → 带时间戳的片段数组 |
| `identify_speakers` | 声纹匹配与身份对齐 | 会议音频 + 参会人声纹 → 带说话人与置信度的片段 |
| `register_speaker` | 声纹注册 | 单人音频 + 姓名 → 声纹向量入库 |

**关键要求**：提供离线固定数据后端。Agent 层与检索层必须能在没有 GPU 的机器上
跑通测试，否则项目无法被他人运行和验证。

### 5.4 检索层

对话式查询的成败取决于这一层，是本项目技术含量最高的部分之一。

| 设计点 | 方案 |
| --- | --- |
| 索引粒度 | 转写片段（含会议 ID、发言人、起止时间、文本） |
| 混合检索 | 关键词检索（人名、专有名词、时间）+ 语义向量检索，再重排 |
| 过滤优先 | 先按会议 / 发言人 / 时间范围收窄，再在范围内做语义检索 |
| 结果融合 | 关键词与向量两路结果用 RRF 融合排序，再交重排精选 top-k |
| 上下文组装 | 命中片段 + 相邻片段（保证语义完整），控制 token 预算 |
| 拒答 | 命中分数低于阈值时返回"未找到"，不交由 LLM 发挥 |

### 5.5 产出层

- `minutes.md`：可直接发群里的纪要正文
- `action_items.csv`：待办表，可导入项目管理工具
- `result.json`：完整结构化结果，供其他系统消费
- `transcript.md` / `transcript.srt`：完整转写与字幕
- 对话记录导出：保留问答与引用来源

## 6. 数据结构（草案）

核心实体：**会议 → 片段 → 纪要 / 待办**，以及独立的 **会话 → 消息**。

```json
{
  "meeting": {
    "id": "m_20260911_001", "title": "官网改版周会",
    "date": "2026-09-11", "duration": 3600,
    "status": "processed",
    "participants": [{ "id": "p_01", "name": "张三", "speaking_seconds": 820 }]
  },

  "segment": {
    "id": "s_0031", "meeting_id": "m_20260911_001",
    "start": 431.2, "end": 448.6,
    "speaker_id": "p_01", "speaker_confidence": 0.93,
    "text": "..."
  },

  "minutes": {
    "meeting_id": "m_20260911_001",
    "summary": [{ "topic": "...", "points": ["..."], "evidence": ["s_0012", "s_0015"] }],
    "decisions": [{ "content": "...", "evidence": ["s_0020"], "confidence": 0.9 }],
    "action_items": [{
      "task": "...", "owner": "张三", "owner_source": "explicit",
      "due": "2026-09-15", "status": "pending",
      "evidence": ["s_0031"], "needs_review": false
    }],
    "open_questions": [{ "content": "...", "evidence": ["s_0040"] }],
    "risks": [{ "content": "...", "evidence": ["s_0044"] }]
  },

  "conversation": {
    "id": "c_0007", "created_at": "...",
    "messages": [
      { "role": "user", "content": "张工这周答应了什么" },
      { "role": "assistant", "content": "...", "evidence": ["s_0031", "s_0066"] }
    ]
  }
}
```

`evidence` 存片段 ID，前端据此渲染时间戳与回跳。`needs_review` 为 true 的
条目不进最终稿，先落到待确认区。

## 7. 关键设计决策

**① 对话是主入口，音频只是其中一种输入。** 不为上传单独做一个页面，避免功能分裂成
"处理工具"和"问答工具"两套入口。

**② 检索优先于长上下文。** 会议库会持续变大，先把范围收窄到相关片段，再交给模型
归纳。这既是成本控制，也是回答质量的前提。

**③ 答案必须可溯源，无证据则明说没找到。** 宁可回答"没找到相关记录"，也不给出
无法核对的内容。这是产品的信任基础。

**④ 感知层与决策层解耦。** 转写和声纹只是工具，接口稳定后替换云端 ASR 或更强的
说话人分离不影响上层。

**⑤ 大模型只走 API，不做本地部署。** 换取模型能力上限与开发效率，代价是调用成本
与数据外发。因此需要配套的缓存、批处理与上下文预算控制，并在界面明确提示音频和
转写文本会上传第三方服务。

**⑥ 显式编排优于单体 prompt。** 拆成工具调用链代码更多，但可调试、可测试、可观测，
这正是 Agent 工程与"套壳"的分界线。

**⑦ 框架只出现在编排层。** LangGraph 负责「什么时候调用谁」，节点内部一律写成不
依赖框架的纯函数，工具层只暴露 Pydantic 契约。这样每个节点都能脱离框架和模型单独
测试，也保留将来替换甚至移除框架的余地。不采用 LangChain 的 `AgentExecutor`：
它的 ReAct 循环不透明，无法对「这句话该走哪条路」做断言。

**⑧ 检索层自研，不封装在 RAG 框架里。** 检索质量直接决定回答质量、成本与拒答
准确性。索引粒度、过滤顺序、融合与重排、拒答阈值都需要逐项调参和量化，包进框架
就失去了调优和讲解的抓手。

**⑨ 前端轻量化，与原型同构。** 界面形态在原型阶段已经定型，正式版用原生前端直接
承接，避免「原型一套、正式版一套」的返工，也省掉前端构建链路。代价是复杂交互要
自己写，MVP 阶段可接受。

## 8. 评测与测试

**功能测试**：感知层、检索层、Agent 层的单元测试全部使用固定样例，不依赖模型与
GPU，保证持续集成可跑。

**效果评测**（固定 3–5 场测试会议，含人工标注的标准答案）：

| 维度 | 指标 |
| --- | --- |
| 纪要质量 | Schema 合法率、待办抽取准确率/召回率、关键结论命中率、负责人归属准确率 |
| 证据可靠性 | 证据正确率（引用片段是否真的支撑结论） |
| 检索效果 | 召回率 Recall@k、命中排序质量、跨会议检索准确率 |
| 对话行为 | 意图路由准确率、多轮上下文保持正确率、无答案场景拒答正确率 |
| 成本 | 单场会议 token 消耗与费用、单次问答 token 与响应耗时 |

其中"拒答正确率"专门衡量会不会编造，是本项目的核心质量指标之一。

## 9. 技术栈

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 前端 | **FastAPI + 原生前端**（HTML / CSS / JS，无构建） | 承接原型的三栏布局与设计令牌；REST + SSE |
| 大模型 | **仅调用 LLM API**（OpenAI 兼容协议） | 适配器封装，切换供应商不改上层代码 |
| 转写 | WhisperX / faster-whisper（本地）或云端 ASR API | 可插拔，见待确认事项 |
| 声纹 | SpeechBrain ECAPA-TDNN | 复用历史项目，支持动态增减参会人 |
| 编排 | **LangGraph**（状态图 + checkpointer + interrupt） | 意图路由、多轮状态、人在回路、长任务恢复 |
| 组件库 | `langchain-core`（消息与工具契约） | 只取零件，不做 Agent 运行时，不用 `AgentExecutor` |
| 检索 | **自研混合检索**：SQLite FTS5(BM25) + 向量召回 + RRF 融合 + 重排 | 参数可调、可量化，不封装进 RAG 框架 |
| 存储 | SQLite + 本地文件目录 | 会议、片段、纪要、会话、人工修改与 LLM 缓存 |
| 数据校验 | Pydantic | 结构化输出的契约与校验，校验失败带错误重试 |
| 可观测 | Langfuse（可自托管） | 工具调用链、耗时、token 与单次成本 |
| 音频处理 | ffmpeg | 统一为 16kHz 单声道 |
| 测试 | pytest | 覆盖感知层、检索层、Agent 层与导出，全部可离线运行 |
| 依赖管理 | 精确版本锁定（`==` 或 uv.lock） | 框架迭代快，面试现场需稳定复现 |

**隐私提示**：音频与转写文本会上传至第三方 LLM / ASR 服务，需在页面与文档中
明确告知用户，并提供本地转写选项。

| 阶段 | 交付内容 |
| --- | --- |
| M1 骨架 | FastAPI 服务 + 轻前端 + 数据契约，对话与会议库跑通（固定样例数据） |

## 11. 待确认事项

以下为仍需拍板的事项；已定稿的技术选型见第 9 节与《技术方案》。

1. **LLM API 供应商**：用哪家（DeepSeek 成本低、通义 / GLM 国内合规性好、
   OpenAI 效果稳定），是否已有可用 Key。
2. **转写走本地还是云端**：本地转写保留现有成果且数据不外发，但需要 GPU；
   云端 API 则任何机器都能跑，但有成本和隐私代价。
3. **会话持久化**：关闭页面后是否需要保留对话历史（技术方案按「保留」设计，
   实现时可降级）。
4. **评测数据来源**：带人工标注的测试会议从何而来（历史录音、自行录制、公开数据集）。

已定稿（v0.3）：前端 FastAPI + 轻前端、编排层 LangGraph、检索层自研混合检索、
依赖版本锁定。
