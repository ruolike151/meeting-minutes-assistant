## 1. 定位：本地库是事实源，Langfuse 是展示层

```text
每轮回答 ──► chat_traces（SQLite，唯一事实源）
                 │  ← 评测报告只从它算数字
                 └─► LangfuseTraceSink ──► Langfuse（看板与排障）
```

这样设计的原因很直接：面试现场可能没有 Docker、没有外网、没有 Key，
但报告必须照常产出。**观测服务不可用时，评测数字一个都不少。**

## 2. 开启方式

```powershell
# 1. 装观测依赖（可选；不装也能跑通全部测试与离线评测）
.\meeting_assistant\Scripts\python.exe -m pip install -r requirements-observability.txt

# 2. 起自托管 Langfuse（首次打开 http://localhost:3000 注册并建项目）
docker compose -f docker-compose.langfuse.yml up -d

# 3. 在 .env 里打开开关并填入项目密钥
MA_LANGFUSE_ENABLED=true
MA_LANGFUSE_HOST=http://localhost:3000
MA_LANGFUSE_PUBLIC_KEY=pk-lf-...
MA_LANGFUSE_SECRET_KEY=sk-lf-...
```

关闭开关（默认）时 `build_sink()` 返回 `NullTraceSink`，**且不会 import langfuse**——
这条由 `tests/test_observability.py::test_disabled_sink_is_null_and_does_not_import_langfuse` 守住。

## 3. 上报字段

每轮对话上报一个 span（`app/observability/langfuse.py`）：

| 字段 | 来源 | 说明 |
| --- | --- | --- |
| `name` | 固定 `chat` | 一轮对话 |
| `trace_id` | `conversation_id` | 同一会话的多轮落在同一条 trace 上 |
| `metadata.nodes` | `answer.trace` | 这一轮走了哪些节点 |
| `metadata.latency_ms` | 各节点耗时之和 | 与本地 `chat_traces.latency_ms` 同源 |
| `metadata.meeting_id` | 范围唯一时的会议 ID | 跨会议问答为空 |
| `usage_details.input/output` | `UsageTracker` | 与本地 trace 的 token 完全一致 |
| `cost_details.total` | 累加费用 | 与本地 trace 的 cost 一致 |

上报失败（网络、Key、SDK 版本）只写一条 warning 日志，**不影响用户拿到的回答**。

## 4. 五块看板与查询口径

以下指标都能用 Langfuse 的 UI 过滤（或直接查本地 `chat_traces`，两者同源）：

| 看板 | 口径 | 对应本地 SQL |
| --- | --- | --- |
| 意图路由准确率 | 路由标注集上的 `intent + answer_mode + scope` 全对比例 | 评测任务 T6 的 `route_gold.json` |
| 拒答率 | `answer_mode = 'refuse'` 的轮数 / 总轮数 | `SELECT answer_mode, COUNT(*) FROM chat_traces GROUP BY 1` |
| 平均 token / 问 | `SUM(input_tokens + output_tokens) / COUNT(*)` | 同左 |
| P95 延迟 | `latency_ms` 的 95 分位（`eval/metrics.percentile` 同口径） | `SELECT latency_ms FROM chat_traces ORDER BY 1` |
| 单场会议成本 | 该会议所有问答 + 纪要链路的费用合计 | `SELECT SUM(cost) FROM chat_traces WHERE meeting_id = ?` |

**口径提醒**：跨会议问答的 `meeting_id` 为空（不硬塞归属），
因此"单场会议成本"只统计范围明确的那部分，报告里也会这么写。

## 5. 版本兼容

`app/observability/langfuse.py` 按"新 → 旧"尝试三种 SDK 接口：

1. `create_trace`（langfuse 2.x / 3.x）；
2. `start_observation`（langfuse 4.x 的 OTEL 风格接口）；
3. `trace`（更老的接口）。

都不匹配时把原因写进 `sink.reason` 并跳过上报——观测是增强，不是依赖。
仓库锁定的版本是 `langfuse==4.15.2`（见 `requirements-observability.txt`）。
